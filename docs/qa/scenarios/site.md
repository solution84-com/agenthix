# Scenarios — `site/`

> Module contract: what `site/` (the Execution Site — the service that runs agent containers on one machine and holds that machine's storage) promises the person who owns the machine. Flat capability list.
> **Scenario ids are unique across every file in this directory**, not per file, because a test cites a scenario by its id alone; the next free id for all of them is `next-sc` in [`hq.md`](hq.md). Ids are append-only: assigned once, never reused or renumbered.
> This file was created on 2026-09-26. Until then the scenarios for the site's runtime — containers, mounts, credentials, dispatch, the control channel — sat in [`hq.md`](hq.md) (for example SC-115 to SC-122, SC-325 to SC-355); they stay there until the full audit of the finished product moves them. No stories or domain map exist for this module beyond what is below; the full audit (a separate unit) writes them.

A site has no browser page, no accounts and no published port. Everything its owner does, they do at the machine with `agenthix-site register | status | unregister`, and everything an admin does about it, they do in hq (see "Execution Sites: approving, revoking, rotating" in [`hq.md`](hq.md)).

## Installing a site

- **SC-430** — A site refuses to start, printing what is wrong and the fix, when its data folder is `/`, a whole home or system folder, a relative path, or a non-empty folder it does not own, or when the host's Docker socket belongs to root with no `docker` group; it never takes ownership of a folder it was refused. · fulfils AC-182a
- **SC-431** — A deployed site publishes no port and serves no page: its one port answers only its agents' endpoints and `/health`, and every other path, `/` included, answers 404; nothing on the network can register, approve or reconfigure it. · fulfils AC-182b
- **SC-432** — A site and its database restart by themselves after a reboot and keep the site's identity across restarts and upgrades; the deployment guide says that deleting the site's database volume loses the identity every project placed on it depends on. · fulfils AC-182c

## Registering

- **SC-433** — `agenthix-site register <hq-url>` prints the address to open and a short code with its expiry, says the code is to be given to an admin of that hq, and waits; the site binds to hq only after both the person at the machine has run the command and an admin has approved; Ctrl-C leaves nothing half-registered. · fulfils AC-183a
- **SC-434** — When registration cannot finish, the command says in a sentence what happened and what to do: an admin denied it; the code expired (run register again); the site is already registered (unregister first); a registration is already waiting; hq could not be reached (it keeps waiting after three failed polls and gives up after twenty-four). · fulfils AC-183b
- **SC-435** — The site never sends its credential over plain http to an address that is not on the machine or a private network, and never follows a redirect while registering. · fulfils AC-183c
- **SC-436** — A machine hq created for itself pairs by the shared secret at every start with no registration; a secret that is too short, or an hq address the site's container cannot reach, is written to the site's log and shown by `status`, not left as silence. · fulfils AC-183d
- **SC-443** — A site can be given a name, at install or at registration, so that two machines are told apart on hq's approval page and lists; a default name is never shown for two sites at once. · fulfils AC-183e

## Knowing where it stands

- **SC-437** — `agenthix-site status` works while hq is down and never prints the machine credential or the pairing secret; it says whether the site is connected, to which hq and since when, and when it is not, the reason in a sentence with the next action — hq unreachable and retrying, hq needs a newer version, the credential was refused. · fulfils AC-184a
- **SC-438** — A site that was revoked while it was off says so on its next start: a credential hq refuses for a site hq knows is reported as "revoked or replaced — register again", not as a network fault retried forever. · fulfils AC-184b
- **SC-439** — `agenthix-site unregister` tells hq, forgets hq, and says what stays on the machine (containers, data folder, database) and how to remove it; if hq could not be reached it says exactly that; for the default site it says the site cannot leave and does not claim that an admin can revoke it. · fulfils AC-184c
- **SC-440** — A site that loses hq keeps trying by itself with a growing delay and resumes without action; a protocol version two or more majors from hq's is reported as needing an upgrade, saying which side must upgrade, never as revoked or offline; after a restart every run that was in flight is reported failed to hq with a stated reason. · fulfils AC-184d

## Limits and responsibilities

- **SC-441** — The limits on what a machine lets agents do are stated where its owner installs it, with their defaults, and can be changed in the compose settings: memory, processors, processes per container, the idle teardown window and the private range agent networks are carved from; the guide also says what a container can reach on the host and on a cloud machine, and which limits (concurrent containers, disk) do not exist. · fulfils AC-185a
- **SC-442** — What is stored on the machine — workspaces, people's credential homes, packages — and who can read it is listed in one place with the owner's responsibilities (the Docker socket, the data folder, the firewall) and the steps when the machine credential leaks: an admin revokes it and the machine registers again; rotation is not a substitute. · fulfils AC-185b
- **SC-444** — The upgrade instructions say that runs in progress fail when the site restarts, and how to let them finish first. · fulfils AC-185c

## Limits on a run (added 2026-10-05)

- **SC-487** — The site enforces the limits hq sends with a run, so they hold when hq restarts: it stops a run, a person's included, once it passes its time limit, and stops a run no person started — one the pulse or a schedule started, or one an agent started with `run_task` — once it passes its turn limit, and a run a person started has no turn limit; an unattended run may finish on its last allowed turn. A stopped run records a reason that names the limit. A site that hq told nothing uses the product's defaults (60 minutes, 100 turns), and a site older than the protocol that carries limits is sent none. · fulfils AC-190c · tests `site/src/agents/runtime/__tests__/runLimitWatch.test.ts`, `AgentEngine.runLimits.test.ts`, `hq/src/agents/runLimits/__tests__/runLimitsService.test.ts`
- **SC-488** — A site runs at most `AGENT_MAX_CONCURRENT_RUNS` runs at once (5 by default), shared by every project and person on the machine. A run beyond the limit waits for a free slot and tells hq it is waiting, so its task shows Running and says so; when it gets its slot it tells hq that it is no longer waiting, and a late or foreign message never changes a task that has moved on. · fulfils AC-190d · tests `site/src/agents/runtime/__tests__/concurrency.test.ts`, `hq/src/sites/channel/__tests__/runWaitingEvent.test.ts`

## Its own logs and diagnostics (added 2026-10-12)

- **SC-764** — Every line the site writes carries a date and time, a level, the source that wrote it and its fields, with secrets removed before it is printed or stored, and goes to standard output and to the site's own rolling log under its data folder (`logs/`), kept for 7 days or 100 MB; nothing is written to disk until the site has started its log at boot, and a log that cannot be written is reported once and never stops the site. The audit line for a tool call names the run, the tool and its risk and never the call's input.
- **SC-765** — `site.readLogs` answers hq with one page of the site's own log, newest first, at errors and warnings unless everything is asked for, narrowed by a time range and a search, with a cursor for older lines; it checks what it is sent, changes nothing on the machine, and the file it reads holds no secret that was logged. A site whose log was never started answers an empty page.
- **SC-766** — The site sends `site.health` to hq as soon as its channel opens and every minute after until it closes: runs executing now against the most it runs at once, the free and total space where project files, workspaces and people's files are kept, whether Docker answers and its version, and whether the agent image is present and the version the site was given (`APP_VERSION`, none when it was given none or the image is absent); a part that cannot be read is reported as unknown or as not running, never as a failure of the whole report, and a report that fails to send is dropped for the next one. `site.healthNow` answers with the same report taken at that moment.
- **SC-767** — `GET /health` answers `{"status":"ok"}` and nothing else about the machine.

## Approval (added 2026-10-12)

- **SC-768** — A run's approval is `bypassed`, `deferred` or `immediate`, and the site's gate applies it to each tool call. A bypassed run is not asked about tool states or command patterns (the harness path rule and a stopped run still bind it). Otherwise a tool or command in the state `never` is refused whatever a request approved; a tool in `ask` that the run was not approved for is refused and listed for a person — a deferred run carries on with the rest of its plan and ends with the list, an immediate run stops at the first one and asks at once; a run with no one to approve it (an unattended run) refuses an `ask` as it refuses a `never`. A command no pattern matches follows the Bash tool's own state ("Any other command"), and a matching pattern wins over it, so an `always` pattern runs while Bash is `ask` and a `never` pattern refuses while Bash is `always`.
- **SC-769** — An approval is for the next run only. Approving a request marks it approved and starts the next run of the task or conversation, which alone is given what was approved, with a note to the agent before its message that is written to no transcript; the run after that gets nothing and its usual levels apply again, and an older approval is never carried past a newer request that was not approved. Starting a run, or any newer message, replaces every request still unanswered in that task or conversation: it is marked replaced and no transcript entry or status frame is written for it. Only the newest run may be approved or denied; approving a replaced or overtaken request answers `approved: false`, and `run.reject` with `replaced` is safe to send twice.
- **SC-770** — ~~`run.resume` is refused with a plain explanation, because a run never waits for approval; approving a conversation's request starts its next run, as a task's does.~~ **Retired 2026-10-21** — `run.resume` is gone from the site protocol at the version baseline; a method a site does not know is answered `unknown_method` (**SC-295**), and approving a request starts the next run (**SC-769**).

## The conversation's whole record (added 2026-10-12)

- **SC-771** — The site records a conversation as its transcript: every row names the run that wrote it, each tool line carries the harness's id for the call and the time the call was made, each stretch of thinking stands where it happened among the calls, and how a run ended is a row of its own — a failure with its reason in plain words, a stop with its cause and who stopped it, an approval asked, and the runtime summarising its memory (with who asked, when somebody did). A run that did things and then failed or was stopped still shows them, and a reply it had written is kept before the stop. A turn that ends with nothing to say records that plainly, except a summary somebody asked for.
- **SC-772** — `transcript.list` gives a person's message its run's current status, so one waiting behind a running reply reads as waiting, and gives an approval request its answer read off its run — who answered, when and the reason a denial gave — reading no runs for a page that needs none; it can return only the tool lines with the given call ids.
- **SC-773** — A message records who sent it and the run it started, and leaves the sender empty when hq names nobody; a task run is given the comments written since its agent last ran on that task (every comment hq sent, for an agent that never has), and records the person it is on behalf of.
- **SC-774** — When the site restarts, every run that was in flight is marked failed, its failure is written into its conversation where the reply would have been, and a failed status is held until hq reconnects and then sent for each.
- **SC-775** — After each run the site records how full the runtime's memory of the conversation is and where the runtime summarises by itself, read from the runtime: from Claude Code's own usage report or, when it is not answered, from the turn's result and its model's window; from OpenCode against the model's limits. It records nothing when the runtime says too little, and says where the runtime summarised, with the summary it wrote.
- **SC-776** — A run dispatched with the hidden summarise request asks the runtime to summarise (`/compact` for Claude Code, the session's summarise call for OpenCode), writes no message and says nothing of its own; the same words typed by a person are an ordinary message.
- **SC-777** — A stopped run records why — a person pressed Stop (and who), a newer message interrupted it, a run limit, or the harness itself — with the words hq shows.
- **SC-778** — `run.listPage` answers a person's runs a page at a time, newest first by when a run started (or was created if it never started), without repeating or skipping a row when several share a millisecond, and can be limited to given tasks or sessions (hq sends those fields only to a site that takes them); a cursor the site cannot read is the first page, and unknown fields are refused.

## Run usage (added 2026-10-12)

- **SC-779** — `run.usage` sums runs on the site in the database, grouped by session (with the model and the person the dispatch named), by agent or by the storage owner the sessions work in, optionally for one agent and for a period (from inclusive, until exclusive, on when a run was created); a run with no usage counts as a run with no tokens, rows carry token counts by kind and the newest run's time, and past 5000 rows the answer says it is truncated. The grouping is chosen from a fixed table and never from caller text.

## A place's files (added 2026-10-12)

- **SC-780** — hq lists an owner's `artefacts/` (the files directly in it, newest first with size and time) and streams one of them by name; the listing shows no folder, hidden entry or link, a folder or entry that is a link is refused without saying where anything is, a name is never a path, a file over the size hq will take is refused before any of it is sent, and the params carry no user id. *(Changed 2026-10-26: an owner's knowledge is no longer a `knowledge/` folder listed and streamed as files; its pages are listed and read as **SC-1391** and **SC-1392** say.)* · tests `site/src/server/storage/__tests__/ownerFolderMethods.test.ts`, `site/src/server/hq/content/__tests__/ownerFolderRead.test.ts`
- **SC-781** — A place's instructions are `AGENTS.md` at the top of its `files/`, put into every run's prompt in that place: it is read only when `files/` is a real directory where the layout puts it and the file is a regular file in it — not a link, not over 128 KiB — and a file that fails any of that is left out of the prompt rather than failing the run; the older `PROJECT.md` is not read.

## Model credentials (added 2026-10-12)

- **SC-782** — A run uses the model credential hq sends with it and the site stores none at rest; a Claude run sent none fails before any container is prepared, saying which boundary has none and where to set one (or hq's own reason, word for word); an OpenCode run, which has providers of its own, is not failed for lack of a Claude credential. A subscription login goes only to a run that runs as the person it belongs to, and a refreshed login is reported back only for that person's own run, never for a project's or a task's. An OpenCode run is refused with a plain reason unless its credential is an API key for the model's own provider (a subscription belongs to the Claude runtime alone, another provider's key and an OpenAI-compatible endpoint with no address are refused), and the key itself never enters the container: the run is given a relay token.

## Conversations, memory and knowledge on the site (added 2026-10-17)

- **SC-1013** — A run states its result with the `set_result` tool, offered to the agent with only the result to give; the site sends hq the calling run's id whatever the agent passed, and nothing when no run of the conversation is going. hq writes it to that run and the task (**SC-970**), and a run that ends without stating one is marked so; only a run states a result. · fulfils AC-319d
- **SC-1014** — A run's home carries the pinned memory as a read-only file when hq sent any, refreshed at every start (**SC-992**); the run's model is the one hq dispatched it with, then the session's, then the agent's without the SDK's date suffix. · fulfils AC-323a

Grep's form, the one hq uses, is **SC-1393**. *(Changed 2026-10-26: agents no longer reach knowledge through this excerpt — **SC-993** is retired — and it searches the owner's pages, not a `knowledge/` folder.)* · fulfils AC-324a · tests `site/src/server/storage/__tests__/knowledgeSearch.test.ts`

## Reaching providers through the relay (added 2026-10-23)

A run's container never holds a provider's key. The site relays its model calls to the provider and reports each call's usage to hq, which is where every call is chosen, kept and costed (**SC-1192**, **SC-1211**).

- **SC-1222** — The relay refuses, without reaching the provider, a request with no relay token or naming no turn, a request between turns or once the run is stopped (403, which Claude Code does not answer by spending its key's ticket), a request from outside its turn's container, a provider the turn has no credential for (naming it), a path that climbs out of the upstream and a provider it does not relay; a bare GET or HEAD of a provider's base it answers itself, with no token. · fulfils AC-364a · tests `site/src/server/modelRelay/__tests__/modelRelayApi.test.ts`, `relayRequest.test.ts`
- **SC-1223** — The provider receives the request as sent — the path and query its SDK added, a body of several megabytes unparsed and byte for byte, a compatible endpoint's request at its credential's own address — with every credential the container sent and every hop-by-hop header dropped and only the turn's key set in the provider's own header. · fulfils AC-364a · tests `site/src/server/modelRelay/__tests__/modelRelayApi.test.ts`, `relayRequest.test.ts`
- **SC-1224** — The harness receives the provider's status and headers, retry-after and rate limits included so its own retry works, and each streamed chunk as it comes and not the answer at its end; a provider that cannot be reached is a 502; the provider's request is aborted when the harness closes its own, and a request still streaming is cut off when its turn ends. · fulfils AC-364a · tests `site/src/server/modelRelay/__tests__/modelRelayApi.test.ts`
- **SC-1225** — The relay's log has one line per request naming the conversation, run, provider, model, status, bytes and timings, and never a key, a token or a body; the model is read from the start of a body as it passes, from the path for Google, and given up on after the start of a body that names none. · fulfils AC-364b · tests `site/src/server/modelRelay/__tests__/modelRelayApi.test.ts`, `relayRequest.test.ts`
- **SC-1226** — A relay token names nothing until it is pointed at a turn, and then only the providers that turn may use while it runs (a turn's own API key and its fallbacks, never a subscription); nothing between turns, once its run is stopped, or once revoked, and a late clear never takes a later turn; an unknown or empty token names nothing; requests still running when the turn ends are cut off. A request is accepted only from its container's own address on a network the site shares with it, or from loopback through a virtual machine's port forwarder, and a container recreated under the same name is read again. · fulfils AC-364a · tests `site/src/server/modelRelay/__tests__/relayTokens.test.ts`, `relaySource.test.ts`
- **SC-1227** — Behind a proxy the relay reaches an https provider through a CONNECT tunnel with the key kept from the proxy, streams through it and reuses it, goes direct for a host `NO_PROXY` names and always for localhost, never sends a keyed http request to a proxy, sends proxy credentials from the URL to the proxy only and to no log or response, and answers 502 when the proxy is down, refuses the tunnel or is not an address. · fulfils AC-364c · tests `site/src/server/modelRelay/__tests__/relayProxy.test.ts`
- **SC-1228** — Every upstream call through the relay is reported with its own new call id, the run, provider, model, usage and status: usage is read from the answer as it passes, which reaches the harness unchanged, from Anthropic's `message_start` and `message_delta` (the delta's count winning, a non-streamed answer too), OpenAI's final usage chunk and its Responses API, OpenRouter's final chunk with cache writes, and Gemini's `usageMetadata` (a stream sent as one array too); a compressed answer is read from a copy and passed on still compressed; an answer with no usage, or in an encoding it cannot read, is still reported; a call that got no answer is unavailable (status 0), an answer broken off is unavailable and one cut off by its turn is no failure; the status and the kind of failure go with it so HQ sees a refused key. Nothing is reported for a run from an HQ that named no provider. · fulfils AC-364d · tests `site/src/server/modelRelay/__tests__/modelRelayUsage.test.ts`, `callMeter.test.ts`, `usageReader.test.ts`

## Workflow runs (added 2026-10-25)

The site runs an approved workflow version that hq sends over the control channel: each step in an executor container of its own (`agenthix-executor`), on a snapshot of the workspace, with its output masked and its changes scanned before anything returns. hq's side is in `hq.md`, *Workflows* and *Workflow runs*.

- **SC-1336** — A run instruction is accepted only when its content hashes to the approved hash: a file, a step, a file's executable bit or the executor image that differs is refused. It is also refused for a step given a secret it doesn't name or missing one it names (no value quoted), values for another number of steps, variables other than those the workflow names, parameters that fail their check again, a secret that is not base64 (not quoted), unknown fields, a run id that could leave its folder, a masking tag out of range, and a repository when no step names `GITHUB_TOKEN`. · fulfils AC-378a · tests `site/src/executor/__tests__/instruction.test.ts`
- **SC-1337** — Starting a run is refused before anything is written or started for a version whose hash differs, a workspace this site doesn't hold, an image it doesn't have, hosts its network can't have, and a run it already has. · fulfils AC-378a · tests `site/src/executor/__tests__/run.test.ts`
- **SC-1338** — `workflow.readFiles`, for a proposal, reads each file with its executable bit and refuses a symbolic link at the file or among its folders (never reading what it points at), a hard link, a missing file, a folder, a file too large, a path that is not normalised or climbs out, and a workspace this site doesn't hold. · fulfils AC-378e · tests `site/src/executor/__tests__/readFiles.test.ts`
- **SC-1339** — The snapshot copies the workspace with its modes and records it by content; the agent writing the workspace afterwards doesn't change it; a symbolic link is copied as a link and never followed; a hard link, whose other name may be outside the workspace, is refused, as is a workspace that is itself a link, and a run whose workspace holds a hard link fails without running anything. · fulfils AC-378a, AC-378e · tests `site/src/executor/__tests__/snapshotWriteBack.test.ts`, `run.test.ts`
- **SC-1340** — Writing back applies the run's created, changed and deleted files; a file the agent changed meanwhile is kept, with the run's copy beside it, and is not deleted; it never writes through a folder the agent swapped for a link, replaces a link the agent put at a file's path rather than writing through it, writes a link a step made as a link, and finds a change by content even when a step set the time back. · fulfils AC-378d, AC-378e · tests `site/src/executor/__tests__/snapshotWriteBack.test.ts`
- **SC-1341** — Each step gets only the secrets it names; the snapshot is bound read-only for a step with a secret and writable for one without; a `./` step runs the version's file, never the workspace's; the first failure ends the run and the rest are skipped; a step's time limit is told from the run's; a stopped step is marked stopped and the rest too; each step is reported as it starts and ends, its output masked for every secret of the place. · fulfils AC-378b · tests `site/src/executor/__tests__/runSteps.test.ts`
