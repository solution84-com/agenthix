Overview · 2

The rule: take the first kind that fits

This replaces "every message is a dialog". It goes into ui/DESIGN-SYSTEM.md under Messages, and the helpers make a builder name the kind.

  1. Known before the press?A refusal on the control: greyed, tooltip says why, pressing opens the full reason.
    As today
  2. Part of the thing shown?A failed reply, a held task, a run's failed step, a form field's error: drawn in the thing.
    As today
  3. A read the screen makes on its own?Opening, polling, refreshing, catching up after a reconnect: a quiet retry. If it keeps failing, a soft nudge where the content would be. Never a dialog.
    New
  4. Something shown is incomplete, and the person can carry on?A site did not answer, a partial search, figures not current: a soft nudge where that thing is.
    New
  5. A conversation's own failure?Stop, Retry, Keep, Summarise, a card's button: a soft nudge in its timeline. A message not sent stays in the message box.
    New
  6. The screen already shows the result?No message.
    As today
  7. Otherwise: a hard alert, the dialogThe person pressed something and it did not happen, a decision cannot wait, or work would be lost. Says what happened, what was kept, and offers Try again.
    Narrowed
A builder's shortcut: did the person just press something? If not, it is never a dialog.

The build · 9

Shared pieces, and the guard that keeps it so

Client behaviour only: no route, message or stored format changes, so no version moves.

PieceWhat it does
NudgeThe soft nudge, drawn in one of its three places; same height with or without it.
One retry policy3 retries at 1, 2, 4 s, not on a final answer; the default for every query in hq, and a retryRead wrapper for hand-written reads and the Fleet Console's polls.
useBackgroundReadNothing during retries or while data is fresh; a nudge after — in place or "Not up to date".
A kind on every messageuseAttentionWhen and ShowAttention require kind: 'alert' | 'nudge'; most callers change one word.
Thread nudgesA conversation's failures as a row after its last message; its own re-reads stop reporting as failed actions.
"HQ is not answering"One app-wide line under the screen bar (if Q4 is yes).
The design guard testRefuses browser alert/confirm/prompt; a message without a kind; a dialog handed a read's failure; a site's silence as a dialog.

Risks the build must cover

  • Silence hiding an outage — the minute rule and the HQ line, both tested.
  • "Nothing here" vs "could not ask" — a nudge in place of the content replaces the empty state, never sits beside it.
  • Layout shift — a height test on Nudge and the designer's check.
  • Double retries — queries with their own retry rule keep it.

Order: re-scan, then the shared pieces as one commit, then lanes by folder (hq, ui, console-web), run one after the other where they could share a file.

A toast: for a result the screen does not show

As a person who just pressed something that worked, when nothing on screen shows that it did, I want a short word that goes by itself, so I know without having to close anything.

Why there is none today: on 6 Nov, choosing one rule for messages, a toast was set aside with a band and a callout, because errors were going to it. It was never weighed for what it is good at. With kinds, an error never goes to a toast, so it can come back for its own job.

Its rules

  • Only for a press that worked whose result the screen does not show.
  • A few words, no buttons; goes by itself after about 4 s, and waits while hovered or focused.
  • One at a time; a new one replaces the last.
  • Bottom centre, above anything at the bottom; never over a control.
  • role="status": a screen reader hears it without being interrupted.

Never for

  • An error: a press that failed is a dialog (Q1); a missable message for a failure is the problem this unit fixes.
  • Something that happened elsewhere (a run finished, a site came back): that is a notification (Q4).
  • A result the screen shows (the role reads Admin): no message.
  • Anything to act on: if it needs a button, it is not a toast.
Recommended: add the toast as handler 3, in layer A (over the page, but it does not stop the person), for a press that worked whose result the screen does not show. The re-scan counts which of today's "no message" results move to it. Not now: an Undo toast in place of a delete's confirm. It needs deletions that can be taken back, which is its own change.
The plan · 14 · Approved 11 Nov

Recount, map, build, verify, with a usability reviewer at every gate

Why the last unit let dialogs through: its reviewer checked how screens look against the design system. Nobody checked what a screen does when something fails. The new reviewer does that, and only that: it never writes code.

1 · Recount and mapread-only agents, in parallel

Find every message again in today's code (the 578 is from this morning). Each gets a row: where, the situation, its kind, its handler (1–16), and what changes. One agent per slice of the code, each writing its own file; the lead merges them into one map with counts per handler.

Gate: the usability reviewer checks the map: every judgement call and a sample of the rest. The owner sees the counts and only the calls it could not settle.

2 · Spec and skill draftthe lead

The boards become the spec; the situation-to-handler table becomes the first draft of .agents/skills/handling-errors/. Then the plan's phases.

3 · Shared piecesone commit, first

The toast, the nudge, the frame line, one confirm dialog, the retry policy, the kind on every message, and the guard test's new refusals.

4 · Move every messagebuilder lanes by folder

Each message moves to its mapped handler. Lanes that could touch the same file run one after the other.

Gate after each lane: the usability reviewer makes things fail on purpose in the running app (network cut, site asleep, HQ stopped) and checks nothing stops the person that should not; the designer reviewer checks the look. At most two rounds back to the builder.

5 · Verifyproof, then the owner's playtest

Recount the same way: every message on its mapped handler, no dialog from a background read, guard test passes. The usability reviewer walks the whole failure list once more. Then the owner's playtest.

6 · Finish the skillonly what was proved

The skill and ui/DESIGN-SYSTEM.md Messages are written from what passed, so the next agent follows it without rediscovering it.

The usability reviewer

What it isA read-only agent: reads code, runs the app in a browser, takes screenshots, writes only its report. Never edits code.
What it checksDoes anything stop the person who did not just press something? Is every failure said by its mapped handler? Can the person carry on? Is anything missable that must not be (a failed press)? Does anything jump or cover a control?
How it ratesCritical (the person is stopped or misled), Should fix (wrong handler, but usable), Minor.
Where it livesRecommended: the organisation's development plugin, beside the code reviewer, so every product can use it; it reads each repository's error-handling skill for that product's rules.
ModelOpus (judgement); the recount agents run on Sonnet.
