Context

Only agents on OpenCode need a search key

The platform picks the runtime from the provider (runtimeFor). Claude Code brings Claude's own search; OpenCode searches only through the platform's web_search tool, which sends queries to Exa with the organisation's key.

D1 · option A, detail

The pop-up behind "Add a key"

One field and a short guide, like the AI step's key guides. It saves through today's setWebSearchKey, so Settings shows the same key afterwards.

  • Says what it's for and that Claude models don't need it.
  • Links to Exa's key page; the free tier is enough to try it.
  • A refused key is said under the field, and the pop-up stays open.
  • Not now closes it; the row stays "not set", and setup is never blocked.

After setup · decision D3

An OpenCode agent with no search key

Recommended: don't offer web_search to an OpenCode run when the organisation has no key, and tell the agent so in its context. When asked to search, it says plainly that it can't and who can fix it, instead of a tool failing mid-run.

  • An admin is pointed to Settings › Access to models and tools › Web search.
  • A member is told an organisation admin can add it.
  • Once a key is saved, the next run has the tool again.

Alternative: keep the tool and make its error say the same thing. Simpler, but the agent learns only after trying.

What changed in the latest Next.js release?
I can't search the web here: I work in OpenCode, and this organisation hasn't added the search key OpenCode needs. An organisation admin can add one under Settings › Access to models and tools › Web search. Meanwhile I can answer from what I know, which may be out of date.

Decision S1

Make Settings consistent in this unit, or after launch?

Recommendation: in this unit. The capability list is built once for setup, so using it on the Models page is mostly reuse. Renaming Voice to Speaking and Listening to Hearing is wording. Shipping setup and Settings with different words for the same thing would confuse the first admins on launch day. The one larger piece, Web search moving off its own page, is a link change; the form stays the same pop-up.

Settings · one page or two

Why Providers and Models are two pages today

Providers: the accounts
  • Each account's key, state and since when, and what the vendor says
  • Who bills for it; Agenthix Cloud's connection
  • Check now, History, Replace key, Rename, Remove, Revoke
  • What depends on it before you remove it
  • The target of "Agents can't answer yet" alerts
Models: the choices
  • The organisation's defaults: model, voice, listening
  • Which models may run, which agents, projects and people can only narrow
  • Says "Keys are on Providers"
The split was accounts against choices. Setup showed that people think of it as one thing: "add what I have, and see what my agents can do". The choices can't be made without the accounts, so every visit to Models starts with a trip to Providers.
Settings · proposed

One AI page, in setup's order

Your providers, then What agents can do, then Which models may run, folded. It's the same order and words as setup's AI step, with Settings' extra tools on each provider line.

For

  • The page matches setup: one mental model
  • Adding a provider and seeing a capability tick is one screen
  • Web search lives with the rest; no separate page

Against

  • A longer page for organisations with many providers
  • Old links (/admin/providers, /admin/models) need redirecting to its sections

The menu becomes Models and billing › AI · Billing profiles · Usage. Alerts link to the provider's line on it.
