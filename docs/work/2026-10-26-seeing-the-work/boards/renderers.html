4 · The renderer boundary

Level 2. Agenthix owns the frame: header, actions, loading, errors, access. A renderer draws only inside the area it's given, from one input: the file's facts and a way to read its bytes from the relay (D17). First-party renderers use the same contract that admin-managed ones would later (file preview).

The shape

After · proposed

1Choosing the kind

One function, in core, so hq and the page agree: name → content type, then the site's look at the first bytes (text or binary). It returns a kind: markdown, text, code, json, csv, image, pdf, or none. It replaces classifyFileContent's closed union.

2The registry

A list of renderers, each saying which kinds it draws and where it runs, looked up by kind. The pattern hq already uses for a place's tools (PlaceTool { id, label, render }). Adding a format is adding an entry, never editing the frame.

3The frame

Today's FileOpened, kept: title, facts, Mention, Download for every kind, Copy path, Copy link. It mounts the renderer and draws loading, "showing part", and every error itself (F2, F4).

4In-page renderers

Text-like kinds, drawn by trusted code as text, never as HTML: Markdown (react-markdown, raw HTML off, as today), text, code (the installed react-syntax-highlighter), JSON, CSV, images. Bytes fetched from the relay with the ticket link.

5Framed renderers

Active kinds, drawn by a viewer page served from the files address, in a frame. PDF first: pdf.js in that page, reading pages by range. If the viewer were ever tricked, it runs where there's no hq session (T7). Admin-managed renderers would run the same way, later.

6Diffs, later

A diff kind (git observability): an in-page renderer whose bytes are a diff the site produces, on a ticket naming two versions. Nothing in the frame or the registry changes for it.

The contract

Narrow on purpose: what goes in, what comes out, and when it ends. It's written once and implemented by every renderer.

// core: what every renderer is given
interface FileFacts {
  name: string; size: number; version: string; contentType: string
  kind: Kind            // 'markdown' | 'text' | 'code' | 'json' | 'csv' | 'image' | 'pdf' | 'none'
  language?: string     // code only
}
interface FileBytes {
  link: string                                  // the ticket link on the relay (D13)
  read(limit: number): Promise<{ bytes: Uint8Array; whole: boolean }>
  range(start: number, end: number): Promise<Uint8Array>
}

// ui: one entry per renderer
interface Renderer {
  id: string            // 'code', 'pdf', …
  kinds: Kind[]
  runs: 'page' | 'frame'
  previewLimit: number  // D14: what it reads at most
  embeds: boolean       // draws in 'embedded' mode too (T3); otherwise the frame draws a card
  // page: drawn inside the frame's area
  render?(props: { facts: FileFacts; bytes: FileBytes; mode: 'opened' | 'embedded'; report: (r: Report) => void }): ReactNode
  // frame: the viewer page's path on the files address
  viewer?: string
}
type Report =
  | { state: 'ready' }
  | { state: 'partial'; shown: number }          // the frame says "Showing the first 1 MB of 3.4 MB"
  | { state: 'failed'; reason: 'unreadable' | 'too-large' | 'changed' | 'unavailable' }
  • In: facts and bytes, nothing else. No hq API, no person, no store. A renderer can't do more than draw.
  • Out: one report, which the frame turns into words. A renderer never draws its own error.
  • Two modes (T3): opened, the whole area with the frame around it, or embedded, inside a page or a message, bounded in size and with no controls. A renderer that doesn't embed is shown as a card the frame draws.
  • Lifecycle: mounted when the file opens, unmounted when it closes or the file changes; reads are cancelled on unmount.
  • A framed renderer gets the same facts and link in its address, and sends the same reports to the frame by postMessage, checked against the files address's origin.

Admin-managed renderers: where they'd plug in

Designed, not built
  • A renderer an organisation's admin adds is a framed renderer: a viewer page served from the files address, never code in hq's page.
  • It declares the kinds or content types it draws and is listed in the registry beside the first-party ones. An admin chooses which wins for a kind.
  • It speaks the same contract by postMessage: facts and link in, reports out. It sees one file's bytes for one ticket's life, and nothing of hq.
  • Not in this epic: installing from a marketplace, renderers that run on a server, editing.

Why this shape

  • One input, because relays alone carry bytes (D17). There's no second path to support.
  • Text-like kinds in the page, because they're drawn as text and can't run, and a frame per Markdown file would be slow.
  • PDF in a viewer page of our own, not the browser's built-in viewer: browsers refuse their own PDF viewer inside a sandboxed frame, and pdf.js lets us read by range and keep the same reports.
