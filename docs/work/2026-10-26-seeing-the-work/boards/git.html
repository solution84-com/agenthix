6 · Git in plain view: what the site reads

Level 2, git observability. The agent does git; the person watches. Everything here is a read of a workspace's own repository on its site, whether or not it has a remote. Git is not GitHub. Status is in the MVP; the rest is stretch (D3).

Today

Before · today
  • The site knows only whether a folder is a repository (getContentState → isGitRepo, site/src/storage/repoOps.ts:73). Nothing reads its branch, status or log.
  • The Files tool's top line is the GitHub backup (BackupLine.tsx): the remote, or an offer to connect one. A repository with no remote shows nothing about git.

  • Read only, always. Nothing here checks out, commits, fetches or pushes. Those stay with agents, and with the workflows work, any git that needs a credential goes through a workflow. Reading local state needs none, so it doesn't touch that design.
  • No fetch to compute ahead/behind: it compares with the remote branch as the agent last fetched it, and says when that was.
  • How the site reads: git run with fixed arguments and a time limit (as repoOps.ts already runs it), never a shell, with GIT_OPTIONAL_LOCKS=0 so a read never blocks an agent's write. A repository's own config can't run anything: hooks, fsmonitor and external diff tools are switched off for these reads (T12).
  • Where: a workspace is one repository. The Files tool reads files/ as one if it is one.

Why this split

  • Status, changed files and logs are small, structured and asked often: they're facts, so they stay on the typed channel hq already uses for listings.
  • A diff is file bytes and can be large, so it goes through the relay like any file (D4, D17).
  • Monaco, suggested in git observability, isn't needed: highlighted code and a diff renderer cover reading, and editing isn't in this epic.
