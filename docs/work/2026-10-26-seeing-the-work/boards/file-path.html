3 · Opening a file: ticket, relay, site

Level 2. One file opened, step by step, from a click to bytes on screen. hq answers one small question, and the bytes go site → relay → browser (D4, D5). The example organisation owns hq.example.com, and its project Alpha lives on site office-server, which relay-2 serves.

The sequence

After · proposed

Step by step

What happensWhere
1A person clicks a file anywhere: the explorer, a task, a chat link, a mention. Every one is the same stable link, naming the owner and the path: hq.example.com/…?tool=files&owner=project:alpha&file=reports/q3.pdf, never a site or a relay (R5).browser
2The page asks hq to open the file. hq checks access (assertLocationAccess, as today) and finds the owner's home site.hq
3hq asks the site about the file, a small typed request on the control channel: size, modified time, a version, a content-type guess from the name, and whether the first bytes look like text. No content crosses.hq ↔ site
4hq picks the renderer kind from that, signs a ticket (R1, R2), records who opened what (T11), and returns kind, size, version and the ticket's link on the site's relay: files-2.example.com/t/<ticket> (D13).hq
5The page mounts the renderer for that kind (board 4), and the renderer fetches the link. A text-like kind fetches the first part it needs; a PDF frame loads the link and reads pages by range.browser
6The relay passes the request down the connection the site opened to it. It reads only the ticket's header to know which site, and checks nothing else.relay
7The site verifies the ticket with hq's public key, resolves the real path inside the owner's storage and refuses anything outside it (T6), checks the version is still the one ticketed, then streams the bytes or the range asked for.site
8The relay streams the bytes back with the sandbox headers (CSP: sandbox, nosniff, no-referrer, and CORS for hq's own address only) (T7, T8). The renderer draws.relay → browser

Downloading

The same, with download as the ticket's purpose: the relay adds Content-Disposition: attachment, and nothing is capped (D14). Every file can be downloaded, whatever its kind or size, which fixes today's gap for binary and over-cap files.

When a relay is down

Relays alone carry file bytes; there is no fallback through hq (D17). hq's relay runs beside hq on hq's own machine (D16), so if it is down, that machine is unwell. Step 4 then answers "Files can't be opened right now: hq's relay isn't answering", and the Fleet Console shows the relay's health. A site on another relay shows the same message, naming that relay, until hq places the site on a working one (D9).

On a bare address (an hq with no files subdomain), hq-web sends one path on hq's own address, /relay/…, straight to hq's relay. Downloads and text-like previews work; nothing is shown inline there (adr-0114), so PDF preview needs a files address.

What's new, by module

ModuleNew or changed
coreThe ticket: its fields, encoding and verification, shared by hq and site. The relay protocol reuses the content channel's stream multiplexer (core/src/protocol/contentMux.ts): the site is the server, as on the content channel
hqThe open operation, the ticket signer and its key, which relay serves which site (D9), and the audit row. classifyFileContent becomes the choice of renderer kind
siteA connection to its relay, and a read that answers only a valid ticket, confined to the owner's storage, by range
relay newA small service of its own: accepts sites' connections and browsers' requests, and passes one to the other. No database. Its own image; hq's relay is in hq's compose set, reached through hq-web (D16)
ui / hq pagesThe renderer registry and renderers (board 4); the frame's Download for every kind
