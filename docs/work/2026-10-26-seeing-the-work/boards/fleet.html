How file bytes move without loading hq, and how that fits the fleet as it may grow. Only hq's relay and the file path are built in this unit; anything marked "later" is an open issue, drawn here only to show it fits. Decided: relays are the only file address, with no tunnel option (D6). The example organisation is self-hosted and owns example.com: its app is hq.example.com and its files are files.example.com.

Why a relay at all

A relay is the fleet's own tunnel: the one public door that sites dial out to, so no site is ever exposed. Ten sites can do the work and hold the files, and one relay serves them all.

  • Most sites can't be reached. A site runs on a laptop, an office server or a rack behind a firewall, and listens on nothing by design (adr-0044, adr-0063). A browser can't reach it; a relay it dials out to can.
  • A site is the last thing to expose. It holds every project's files it carries and runs agents. A relay holds nothing and decides nothing; it only passes bytes for a ticket the site checks.
  • One address and certificate per relay, not per site. Adding a site never means a new public name.
  • The separate address is the browser's safety wall (adr-0114): an agent's file opened at the relay's address can't act as you in hq.
  • A site never has a door, not even beside a relay on its own machine: a machine is a site or a relay, never both, outside hq's machine (D22). For speed, a relay goes near the sites it serves, on a machine of its own.

The layers: what each machine is for

This is a picture to think with, not a plan. Only the relay's file path is in this unit; everything else marked "later" is an open issue. There are three kinds of work, each with its own kind of machine, and every machine dials out to hq.

One organisation's fleet
The rule that holds it together
  • hq decides, it doesn't carry. It checks access and chooses placement: which site holds a space, which relay serves a site, and where a burst run goes. It issues tickets.
  • Relays carry, they don't decide. The only file address there is, with no tunnel option. They pass bytes between machines and browsers. A site checks every ticket.
  • Sites hold and run. A space has one home site. A burst site borrows a copy for a while and owns nothing.
  • Every machine dials out and is enrolled in the Fleet Console, so a laptop or an office box behind a firewall is a full member.
What this unit builds of it
  • In: the file ticket, hq's relay in the compose file, sites dialling it, and the browser fetching files from it. No fallback through hq (D17).
  • Designed for, not built: more relays, and hq assigning sites to them.
  • Not ours: burst sites and checkout, shared rooms, and hq as several copies, all proposed elsewhere. The picture only shows that they fit.

The network: where each machine sits, and who dials whom

Where each machine sits and who connects to whom. An arrow points from the side that opens the connection to the side that listens. Only front doors listen to the internet, each on 443: hq's and each relay's. Everything else only dials out.

One organisation on the internet
Who listens
  • hq's front door, at two names: the app, and hq's relay.
  • Each extra relay's front door (relay-2).

No site listens on anything. The office, the home and the rack open no port, because every arrow out of them points away from them.

Opening a file in project Alpha
  1. The browser asks hq.example.com, and hq checks access. Alpha's home is office-server, and office-server is served by relay-2, so hq returns a ticket for files-2.example.com.
  2. The browser asks files-2 with the ticket.
  3. relay-2 passes the request down the line office-server opened to it.
  4. office-server checks the ticket and streams the file back up that same line.

hq handled one small request, and none of the bytes.
