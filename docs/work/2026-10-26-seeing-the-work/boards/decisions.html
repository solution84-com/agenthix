Questions and decisions

The questions raised while designing, how each was decided, and the defaults the design applies. The spec is written from these boards. One epic in three parts: file preview, git observability, and IDE access.

Status

  • How the boards work: architecture is numbered 1–8; the UI is grouped by where people meet it (F, T, G, R, I). Architecture and UI feed each other. A UI board that needs something new adds it to an architecture board, and an architecture choice shows up in the UI boards it touches.
  • Every board is drawn: architecture 1–8; UI F1–F4, T1–T3, G1–G2, R1, I1. Reviewed as a whole and settled on 25 Oct 2026.
  • What they are for: the build baseline. The spec and the plan are written from them.

Open questions

None. Q1–Q4 were answered on 25 Oct (D8–D11), Q5 on board 8 (D12–D15), Q6 as D17 and Q7 as D18. Q8 (D19), Q9 (D20) and Q10 (D21) came up in review: files shown embedded (T3).

Recommended defaults

Applied unless a decision says otherwise.

DefaultBoard
R1hq signs tickets with a key only it holds (an asymmetric signature). Sites verify with hq's public key, so neither a site nor a relay can make a ticket.3, 8
R2A ticket binds one file, one person, read or download, and a short expiry (minutes). It's refused if the file changes underneath it.3, 8
R3Text-like kinds are drawn in the page (Markdown, text, code, JSON, CSV, images, later diffs), from bytes fetched at the relay's address. Active kinds (PDF now, admin-managed renderers later) are drawn in a sandboxed frame loaded from the relay's address. One contract for both.4
R4Relays are enrolled like sites: by a fleet admin with a one-off code, listed and removable in the Fleet Console.5, R1
R5One stable link per file, the same from the explorer, a task, a chat or a mention, opening the file in place. The address names the owner (project or person) and the path, never a site or a relay.3, T2
R6Git status is read on demand from the site when a workspace is opened, over the existing typed channel, not pushed.6, G1
R7A relay's address is the files address. The files origin that exists for uploads (adr-0114; the platform's FILES_ORIGIN) becomes the address hq's relay answers on, and each further relay gets one beside it. For a self-hosted fleet, the organisation's own name, which its admin sets as FILES_ORIGIN: files.example.com, then files-2.example.com. A hosted fleet uses names on a domain kept for files alone, apart from the app's, so that a file reported as harmful can't take the app's name down with it. Every file byte now gets the protection the files address was made for. With no files address (a bare address), hq's relay answers on a path of hq's own address (D17).2, 5, 8
R8The relay carries streams, not just files. Each stream is opened with a ticket naming its purpose (preview, download; later diff, ide-session, live previews). Files are its first purpose, and each kind of traffic may have its own line from the site, so a large download never slows an IDE session and a site can refuse a kind it has switched off. The MVP builds one line, for files, on the content channel's stream multiplexer, and narrows nothing to files. Why it matters: people will want their own IDE for the file types Agenthix will never preview, such as their own app's formats, and that must arrive without a new door or a rebuild.3, 5, 7

Decided

DecisionWhen
D1One epic, three parts: file preview, git observability, and IDE access. Seeing what agents produced is the point: people can direct agents but can't yet properly see their work.25 Oct
D2The unit is the epic: designed whole, built MVP first. The spec covers all three issues. The plan builds the MVP, then adds each stretch phase if time allows, each one droppable without loss.25 Oct
D3The MVP line. MVP: the renderer boundary; download any file; plain text and highlighted code; JSON and CSV; PDF and more images; opening from tasks and links; git status at a glance. Stretch: YAML, HTML source and Markdown with relative images; changed-file markers; diffs; log, branches, ahead and behind; the IDE proof of concept. Designed, not built: admin-managed renderers; how an IDE session is authorised.25 Oct
D4hq decides, it doesn't carry. Organisations work the same hours with hundreds of agents running, and hq is already relaying their messages, so file bytes don't pass through hq. Approaches A–C, which all funnelled through hq, are set aside.25 Oct
D5Relays as fleet members. A relay is enrolled with hq like a site. Each site dials out to the relay hq assigns it, and hq puts that relay's address on the ticket. That's sharding with hq as the router, not a load balancer. A relay only passes bytes; the site checks every ticket. Default: one relay in hq's compose file, with more relays on other machines as an org grows.25 Oct
D6No tunnel option. A tunnel service (such as cloudflared, run by the organisation or provided for it) was considered as an optional way for a site to serve files, and so was a site's own direct front door. Both were dropped: they add complexity, another vendor and cost, for little benefit over a relay. A site that wants a relay of its own gets one on a machine nearby, never its own (D22). How an operator exposes a front door is deployment. How an hq with no public address is reached is outside this design.25 Oct
D7Not a copy in object storage. Copying files to a bucket on open was weighed and set aside for live workspace files: a second copy of the org's files, a wait on first open, copies going stale, and it would reverse adr-0026. It may suit finished artefacts later.25 Oct
D8Fallback through hq Replaced by D17. Was: fallback through hq when a site has no relay, or its relay is down: streamed and capped. An admin setting can turn it to downloads only or off. (Q1)25 Oct
D9hq places sites on relays automatically, on the least-loaded enrolled relay, rebalancing when a relay is added or lost. An admin can pin a site to a relay. (Q2)25 Oct
D10Live previews stay on hq in this unit. The relay is designed so they can move later, raised as its own issue under the epic. (Q3)25 Oct
D11No mobile file preview in this unit. The ticket and the relay work for any client; the app adds preview in its own repository later. (Q4)25 Oct
D12A relay sees the bytes it carries, as a site sees the files it holds. Both are fleet members, enrolled and trusted alike; making the relay blind (TLS passthrough) would ask more of it than of the site. Whoever runs a fleet machine is trusted with what it holds or carries. (Q5 · S1)25 Oct
D13The ticket travels in the link to the files address, good for a few minutes and reusable until then, as uploads already are (adr-0114). Not a cookie (third-party, blocked by Safari), not a header (a PDF frame or a download can't send one). (Q5 · S2)25 Oct
D14The caps (board 8): text drawn to 1 MB, and no more on purpose. A larger text file is a smell; it gets Download, and a real need is a change request (pagination), not a raised cap. Code highlighted to 512 KB; JSON 5 MB; CSV 10,000 rows; images 20 MB; PDF 50 MB, by ranges. Relay downloads uncapped. 16 streams per person; 32 reads per site; tickets live 5 minutes. All but the text cap are admin settings. (Q5 · S3)25 Oct
D15The proposed defences T1, T4–T9 and T11 stand (board 8): signed tickets, enrolled relays, tickets per file, symbolic links confined, a separate origin with sandbox headers, reads only from hq's address, expiry instead of revocation, audit at hq. (Q5)25 Oct
D16hq's relay: a default relay that just works, as hq's site does. Developers run Agenthix on their own computer, so the relay must need nothing set up.
  • Always there: hq's machine carries hq, hq's site and hq's relay, in the same compose set.
  • Connected by configuration, not enrolled: joined to hq by a shared secret, like hq's site (adr-0070). Further relays are added by a fleet admin in the Fleet Console, like further sites (adr-0115).
  • No new port: reached through hq's one published port (adr-0067). hq-web sends the files host to the relay, so a front door is still optional.
  • On a laptop: it answers at files.localhost, which hq already uses on localhost (hq/src/server/files/filesOrigin.ts). Previews and downloads work out of the box with nothing to configure.
  • Where nothing else is set: every site is placed on hq's relay until another relay exists (D9).
  • One of each per machine: a machine carries at most one hq, one site and one relay, extending adr-0108. Outside hq's machine, never a site and a relay together (D22).
25 Oct
D17Relays alone carry file bytes; no fallback through hq (replaces D8). hq's relay runs on hq's machine, so if it's down, hq's machine is unwell anyway; a fallback would be a second byte path to build, secure and test forever, with its own caps and a second input for every renderer. When a relay is down, the viewer says so plainly and the Fleet Console shows its health. On a bare address, hq-web sends a path on hq's own address to hq's relay: downloads and text drawn as text, never inline (adr-0114), so hq-server still carries nothing. Only PDF preview needs a files address. (Q6)25 Oct
D18hq's relay serves the files hq keeps itself: task attachments and the pictures of agents, people, teams and the organisation, read from hq's upload folder, mounted read-only beside it on hq's machine. hq-server stops serving bytes altogether, so "hq decides, relays carry" holds for every file. Rejected: moving attachments to sites (a migration this epic doesn't need), and leaving uploads with hq-server (two byte paths). (Q7)25 Oct
D19Embeds in the MVP: one Markdown embed, everywhere Markdown is drawn. Relative images in Markdown files, knowledge pages, a task's description and comments, and agents' replies, which are already Markdown (MarkdownMessage), so an agent shows an image by writing ![…](files/…) and nothing new is needed in replies. Other kinds as cards. Images from other websites wait for a click. A person adding an image to a conversation is stretch. (Q8)25 Oct
D20A person's images in a conversation belong to the conversation's place, and only Agenthix serves them (stretch). Kept on the place's site but outside what runs mount, as agent knowledge is (agenthix 2026-10-25-agent-knowledge: {site}/knowledge/…, never mounted): here {site}/uploads/<place>/<conversation>/. People reach them through the relay with a ticket; agents only through Agenthix's tools, scoped to the conversation, never by reading the file system. A run gets one only when the conversation hands it over. (Q9)25 Oct
D21A conversation's files are the room's files. An image added to a conversation is visible to whoever is in that conversation, and no one else: today its owner, as a chat's content is private to its owner (adr-0041, adr-0077). When conversations can include several people (later, as shared rooms are proposed), the files stay in the conversation, and inviting someone in is how they see them. Sharing beyond the room is a deliberate step: Save to Files (or asking the agent to) copies it into the place's Files; or attach it to a task, which publishes it to the project. (Q10)25 Oct
D22A machine is a site or a relay, never both, outside hq's machine, which carries hq, hq's site and hq's relay behind the door hq already has. Opinionated on purpose: sites dial out so that they're never exposed, and a relay needs a door, so a relay beside a site would expose the machine holding the files. It would buy almost no speed: the bytes leave the site's network once either way, and what costs time is distance, which a relay in the same region solves. When hq's relay isn't enough, add a relay on another machine, near the sites it will serve. Revises D6's "runs a relay on its own machine" and D16's "a site's own machine may run a relay beside it". The Fleet Console's Add asks a site or a relay, with no Both.25 Oct
D23A sized image tag in Markdown. Besides ![alt](path), Markdown accepts <img src alt width height>, as GitHub's does, so an image can be sized. It's the only HTML accepted: those four attributes are kept and everything else is dropped; every other tag stays text, as today. src resolves like a Markdown image: a file in the place through the relay, a path out of the place shown broken, another website behind Load. (Raised in review, from GitHub's own image tags.)25 Oct

Notes for the spec

  • Decision records (written once each is called made): relays as fleet members and file bytes off hq (D4–D6), amending adr-0063 (every byte through hq) and adr-0114 (the files origin); the renderer boundary.
  • Fits, not built: burst compute and checkout, shared rooms, and hq as several copies, all proposed elsewhere. A checkout's bytes could travel through a relay too.
  • A hosted service could run relays for an organisation, as it could run sites; nothing here depends on it.
