# The v0.1.0 schema — plan

**Status:** approved 2026-11-15; built, closing. Operational work: no design spec. The decisions are below.

## Goal

`v0.1.0` starts from a clean schema. Each app has one initial migration, which gives exactly the schema the code
uses, with nothing left over from the alpha period. The squash goes out first in an alpha, and every installation is made
fresh from it. From the squash on, every migration keeps rows.

**In scope:**
- both schemas (`hq/schema.prisma`, `site/schema.prisma`) reviewed against the code, and what nothing uses removed;
- the out-of-date defaults and the subtasks field settled;
- each app's migrations squashed into one;
- the migration check and the upgrade test made to cross the squash;
- the rule written down;
- every protocol restarted at 1.0, with every deprecated piece removed and the snapshots recorded again;
- the squash cut as an alpha, and the alpha installations reinstalled from it.

**Out of scope:**
- carrying alpha data. The alpha installations (the reviewers' HQ and the demo) are reinstalled, not upgraded
  (owner, 2026-11-15);
- new schema features;
- the rest of the versioning rules (alpha and rc after `0.1.0`), which are their own work.

## Size

**Medium.** The review touches every model in two schemas. The squash itself is mechanical but must be proved exact.

## Approach

One branch, `chore/v0.1.0-schema`, cut from `main` after alpha.5.

**The squash goes out in an alpha before `v0.1.0`** (owner, 2026-11-15). This branch merges, and the next alpha
(alpha.6) carries the squash. The alpha installations
are reinstalled from it, since a squash ends upgrades from the alphas before it. The squashed migration needs no
upgrade of its own to prove it: every install from alpha.6 runs it, and the release build's install test runs it on
every cut. The first migration on top of it is proved like any other, by the migration check and the upgrade test.

Phases 1 to 5 run on this branch. The full regression runs at the close, then one merge. Phase 6 is the cut after it.

**Why the schema edits need no migrations of their own:** the squash generates one initial migration from the
schema as it stands. Removing a model, a column or an enum value is an edit to `schema.prisma` and to the code that
named it. The squash takes it in, and no installation has to carry the old shape.

## Work breakdown

### Phase 1 — Both schemas reviewed against the code

- [x] 1.1 An inventory of every model, field, relation, index, enum value and default in both schemas, each checked
      against the code that reads and writes it (hq's operations and server code, the site's server, core's types,
      the seeds and tests). Each gets **keep**, **remove** (nothing reads it, or nothing writes it) or **fix** (a
      default the code overrides). The list is the review's record, in `execution/schema-review.md`. The owner reviews
      it on a board before anything is removed
- [x] 1.2 The known items:
      - #311: `OperationState.SCHEDULED` and `Operation.seenAt`, written by nothing;
      - #243: `Board.columns`' and `Agent.defaultModel`'s defaults, out of date;
      - #227: `update_task` offers `subtasks`, which has no column. Removed from the tool and its instructions
        (owner, 2026-11-15)
- [x] 1.3 The removals and fixes made, with the code that named them, each module's typecheck and tests passing

### Phase 2 — Each app's migrations squashed into one

- [x] 2.1 hq: its 44 migrations replaced by one, `<timestamp>_init`, generated by Prisma from the reviewed schema
      (`prisma migrate diff --from-empty --to-schema-datamodel`, as the `database-migrations` skill says for hq under
      Wasp). `migration_lock.toml` is kept
- [x] 2.2 The site: its 8 migrations replaced the same way. Its image applies them at start (`migrate deploy`), so
      nothing else changes there
- [x] 2.3 **Proved exact**, for each app:
      - the new migration on an empty database gives no difference from the schema (`migrate diff` from the
        migrations to the schema, empty);
      - the old chain plus phase 1's edits gives the same schema as the new migration. The only differences are the
        reviewed removals and fixes, listed against 1.1
- [x] 2.4 What names a migration updated: the test fixtures in `scripts/__tests__/regression-changes.test.mjs`, and any
      test that applies the migrations

### Phase 3 — Every protocol starts clean at 1.0

The five protocols moved through the alpha period: client 1.23, site 1.19, host 1.3, relay 1.2, Cloud 1.1. They carry
99 deprecated pieces (82 on the client protocol, 17 on the site's) that only alpha peers need. Every alpha installation
is reinstalled, so v0.1.0's baseline is 1.0 everywhere with nothing deprecated. From then on, a deprecation is one a
real user's peer depends on. ADR-0136 restarted them once already, at alpha.1, for the same reason.

- [x] 3.1 Every deprecated piece removed, with the code on both sides that still reads or writes it: hq, the site,
      the host service, the Fleet Console, the relay and core
- [x] 3.2 Each protocol's constant set to `1.0` and its snapshot recorded again (`npm run snapshot:update` in core,
      whose rules must allow a deliberate reset; if they don't, the reset is a step of its own in the snapshot tooling)
- [x] 3.3 The other peers: the mobile app starts at the client protocol of `v0.1.0` (no one runs it yet, so it
      needs no change before the cut; owner, 2026-11-15). Agenthix Cloud's side resets its expected version with the
      cut; its maintainers are told which cut carries the reset
- [x] 3.4 `versioning.md`'s history of each protocol's alpha minors replaced by the 1.0 baseline

### Phase 4 — The release checks cross the squash

- [x] 4.1 The migration check (`scripts/migration-check/run.sh`) and the upgrade test (`scripts/upgrade-test/run.sh`)
      start from the newest tag, whose history the squash replaces. Each recognises a squashed history (the tag's first
      migration isn't the tree's) and is skipped, saying why: *"the migrations were squashed after <tag>; an
      installation of <tag> is reinstalled, not upgraded"*. From the first tag after the squash, both run as before
- [x] 4.2 The full regression passes on the squashed branch. *Release* is proved by alpha.6's own run (6.1): its
      release build and install test install fresh

### Phase 5 — The rule written down

- [x] 5.1 `AGENTS.md`, `docs/architecture/versioning.md` and the `database-migrations` skill: the clean-slate rule comes
      out. From the squash on, every schema change keeps rows (add, backfill, then tighten), and the migration check
      proves it. This is the migrations part of planned work tracked outside this repository
- [x] 5.2 The guide and the deployment document: an installation from before the squash is reinstalled. Nothing a
      user can reach says this, since the squash comes before the first release

### Phase 6 — The squash cut

- [ ] 6.1 alpha.6 cut with the squash. The alpha installations reinstalled from it

## Key decisions

| Decision | Why |
|---|---|
| A plain squash, no baseline for existing databases | The only installations are ours, and are reinstalled (owner, 2026-11-15) |
| The squash goes out in an alpha before `v0.1.0`, installed fresh | It is proved on real installations before `v0.1.0` makes it permanent; a fresh install is all it needs (owner, 2026-11-15) |
| Schema clean-up before the squash, with no migrations of its own | The squash takes in the cleaned schema; nothing needs to carry the old shape |
| `subtasks` removed from `update_task` and its instructions | Nothing stores it; a task's board and parent cover it (owner, 2026-11-15) |
| The owner reviews the schema list before anything is removed | Removals are hard to see in a diff; a list with the evidence for each is easier to judge (owner, 2026-11-15) |
| Every protocol restarts at 1.0 with nothing deprecated | Nothing outside the team runs an alpha; v0.1.0's peers start from one baseline, and every later deprecation protects a real user (owner, 2026-11-15) |
| The checks skip across the squash and say so | They start from the newest tag; one release crosses the squash, and a silent pass or a failure would both mislead |
