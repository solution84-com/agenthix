2c · Identity and dependencies

Does a skill have an identity of its own, and does an agent template carry its skills or point to them? Worked like a package registry (pub.dev, npm), so nothing a template needs can disappear.

Today

  • A library package already has an identity. Every library item (an agent, a board, a skill, a team) exports as one ZIP with a package.json: kind, name, version, publisher, source (built in, made here, marketplace). Its comment says it is shaped "so a marketplace can later deliver the same packages" (hq/src/library/packages/packageManifest.ts).
  • Nothing declares dependencies. An agent package carries its skills inside it (skills/<slug>/), and a team carries a shared pool. Both are self-contained, which is why the 26 copies exist and drift.
  • An installed skill forgets where it came from, apart from an installed_from pointing at a row in this hq.
  • adr-0072 dropped agent versions. It noted that holding one project on an older version "is a need a shared marketplace has".

Two ways a template can hold its skills

Self-contained (vendored)
  • The template carries copies.
  • For: never missing; unpack it anywhere and it works.
  • Against: every copy drifts. A fix to the shared skill reaches no template. Two agents from different templates carry two versions of "the same" skill.
References (dependencies)
  • The template names the skills it needs.
  • For: one skill, fixed once; templates stay small.
  • Against: a name can stop resolving (deleted, renamed, never installed), and the agent arrives missing part of its job. That is your concern, and the one every package registry has had to solve.

Proposed: both, with a registry's rules

1Every skill has an identity

publisher/name plus a version, from the manifest that already exists. Examples: agenthix/qa-bug-reporting 1.2, an organisation's own fernhill/release-notes 3. The name a run uses (source-slug) is unchanged.

2Bundled: a template's own role skills

Written for that role, and they refer to each other (the project manager's read-context "must run before any other skill"). They live inside the template's package with identities under it (agenthix/project-manager/read-context), travel with it, and aren't offered alone. Like npm's bundled dependencies.

3Dependencies: shelf skills it names

The manifest lists them with a version range: agenthix/qa-bug-reporting ^1. Team templates do the same, instead of carrying 26 copies.

4Rule: it resolves, or it isn't published

A template is exported or published only if every dependency resolves. In this hq that means the shelf or the organisation's skills; later, the marketplace. The check is the same one pub.dev runs on upload.

5Rule: a published version never disappears

A version, once published, is never changed or deleted, only marked deprecated or withdrawn, as pub.dev retracts and discontinues. So nothing that depends on it can break. It's the same rule the platform's own releases follow.

6Installing resolves

Creating an agent from a template installs its bundled skills with it. For each dependency, hq reuses an installed skill whose version fits, or installs one. The agent records the exact version it got, like a lock file. A newer version that fits is offered as an update, never applied by itself.

7Removing something depended on

hq names the agents that depend on it and asks first. If you go ahead, they keep working without it, and their pages show missing: qa-bug-reporting with Install. Nothing breaks silently.

8Between hqs, with no registry

An exported ZIP vendors its dependencies, so it is self-contained in transit, and importing de-duplicates by identity and version. A self-hosted hq without the marketplace still shares whole templates. When the marketplace comes, references resolve against it instead.

Why this shape: it takes the self-contained template's guarantee (unpack it and it works) and the reference's single source (fix once). It's the shape package registries settled on, and it is the foundation the later publishing work needs. Only skills use it in this unit (D2). Agents and boards keep their manifests as they are.

Revised: one rule for everyone, every package carries what it needs

Raised 27 Oct: letting only Agenthix's packages hold references would make the experience inconsistent, with some templates able to point to skills and others not. And with packages coming from anywhere (D7), references for everyone would need a resolver across every source, with skills that can go missing.

Where the drift really comes from: the 26 copies are hand-kept copies in our source, not a flaw in self-contained packages. Fix the drift where it starts, and packages can stay self-contained.

The file levels: observed, not controlled

V1–V6 are for installed skills: the ones hq holds (L2 the organisation, L3 an agent). Skills in files, in a place (L4, L5), a workspace's repository (L6) or a person's own space, belong to whoever owns those files. hq can't pin them: a file changes when someone writes it, and a repository changes when someone commits.

What hq can do with a skill in files
F1Its version is its content. The site reports each skill folder's fingerprint, and each run records the fingerprint it used. "What ran" is answered for files too.
F2History is the owner's. A repository has git's history (L6). A place's files/ has none of its own, so hq keeps the fingerprints it has seen, to show changed since.
F3Knowing where it came from. A skill copied in with Add to this place records its identity and version in its metadata. hq can then show "agenthix/pm-sprint-planning 1.3, edited here" or "1.4 is available", and offer to overwrite it. It's an offer, never enforced.
F4On or off by fingerprint: the gate in Q3. That's the only control hq has over files, and it covers agent-written skills too.
F5The same skill in files and installed: when a place's files hold a skill whose identity is also installed for the organisation, the organisation's installed version wins, and the file copy is set aside (D12).
How Claude Code settles F5: enterprise beats personal, and personal beats project, so the managed copy wins a clash. Applied here, the organisation's installed version wins for the same identity. The file copy is not staged, and the place's Skills page shows it as set aside: the organisation installs 1.4. A skill with a different identity, or none, is never affected.

Copies and credit (D18, D19)

  • Edit an installed skill and it becomes your copy: agenthix/code-review 1.3 edited by Fernhill becomes fernhill/code-review, made here, and takes the original's place. The original is set aside, and upstream updates show as news.
  • Provenance is written once, when the copy is made: the manifest's basedOn list, inherited and extended by one dated line. hq never changes it afterwards, and people can only add stated credits.
"basedOn": [
  { "skill": "agenthix/code-review", "version": "1.3", "fingerprint": "sha256:9f2c…",
    "copied": "2026-10-27", "recorded": "hq" },
  { "skill": "blog.example.com/review-checklist", "copied": "2026-10-27", "recorded": "stated" }
]

Shown as verified where hq can match the fingerprint, and as stated otherwise. The licence travels with it.

Who is the registry: Agenthix, never an organisation

Raised 27 Oct: if every organisation can publish packages with dependencies, each hq becomes a registry beside ours. That's two registries to maintain, plus the dependency logic inside every organisation's templates. Instead, Agenthix is the only registry, run as a hosted service. An hq installs; it never publishes.

Self-hosted: how do new skills reach an hq?

The catch in G1–G6: if only Agenthix publishes, a self-hosted organisation gets new skills only from hq releases, or by registering with a hosted service to pull. Must it register with us just to install?

What self-hosters expect, from the tools they already use

The expectation:
  1. Installing the public catalogue needs no account.
  2. What ships works offline.
  3. Your own things are used privately, without publishing anywhere.
  4. You can point at your own source, increasingly just a git repository, instead of running a registry.
  5. An account is needed only to publish publicly.
Requiring registration to pull would read as lock-in to a self-hoster.

The options

A · A hosted registry only; register to pull
  • For: one channel; we know every installation.
  • Against: breaks expectations 1 and 4. An air-gapped organisation is stuck with each release's snapshot. Works against "nothing withheld from self-hosted".
B · A hosted registry, anonymous pull; publishing needs an account
  • Pull: any hq installs Agenthix's and, later, published packages with no account. The snapshot in the image covers offline use.
  • Own: local skills (G4) and ZIPs between hqs.
  • Against: no way to share privately across an organisation's several hqs or teams except ZIPs. Expectation 4 is unmet.
C · B, plus git repositories as sources (recommended)
  • As B, and an administrator can add a source: a git repository holding skills in the Agent Skills format (folders with SKILL.md). That's the format Claude, Copilot and Cursor share, and how teams already keep them.
  • Nobody runs a registry. The repository is the private catalogue, as Claude Code's plugin marketplaces are.
  • Simple on purpose: skills from a source are self-contained, with no dependency ranges, so hq needs no resolver for them. Dependencies resolve only against Agenthix's registry (G5).
  • Against: a private repository needs a credential. That has to go through the workflow and secrets rules, not a token in hq. More to build than B.
D · Organisations run their own registry server
  • What we want to avoid: two registry implementations to keep in step, as above.

For the release

Whichever is chosen, 0.1.0 needs only: the snapshot in hq's image, the organisation's own skills, upload of a folder or ZIP, and ZIP export. A hosted registry and git sources come after, and the shape leaves room for both.
