7 · In a conversation: pick, invoke, record

What happens between a person typing / and the work step that opens the skill Ada used, and how agents learn what skills are. Numbers match the diagram. Screens: C1, C2. Spec part 5.

The path

Each step

1The picker's list

New hq query: listConversationSkills, given the conversation. hq resolves what this run would stage (spec part 5): built-ins not switched off, installed skills Ada has, the place's switched-on file skills, the person's published personal skills, after the clash order (D16). It leaves out anything set aside, switched off, or marked user-invocable: false. Each item: display name, description, level, identity and version, staged name.

2The message carries a field

Protocol change: the message hq sends a site gains an optional skill (the staged name). The text is never rewritten (R3). It's a new optional field, so the site protocol's minor version moves (versioning.md).

3The site validates it

Accepted only if it equals a name staged for this turn whose skill allows invocation; otherwise it's dropped and the text kept (security review M7). Text beginning with / is escaped either way, so the runtime never parses a command, bundled ones included (T7).

4The runtime's own form

Claude: the turn's user message is built in claude/turnInput.ts, which today pushes plain text; with a skill, the turn begins with an explicit instruction to use that skill through Claude Code's Skill tool, in the staged plugin (claude/claudeSkills.ts). OpenCode: the same instruction, and Agenthix's plugin skill tool loads it from the conversation's staged folder (opencode/openCodeSkills.ts). Same words on both runtimes.

5The agent loads it

A Skill / skill tool call, gated as today: a name not staged is refused (skill-not-staged, sdkToolGate.ts). The agent may also load a skill on its own when a task matches its description: the same call, with no picker.

6The site records what ran

Per run, a table from staged name to level, identity, version and fingerprint, written when staging. The tool call is looked up in it, so the step names the skill a person knows, not org-dev-code-review.

7The work step

core/src/protocol/workSteps.ts: the skill spec gains a target. WorkTarget today is task, board or file; it gains { type: 'skill', name, identity, version, fingerprint, level }. The step reads Used the skill Code Review · Fernhill · 1.3.

8Opening it

The step opens the skill beside the conversation (ShownViewer.tsx's Beside panel) at the fingerprint the run used, from hq's kept content (D26). Access is checked when it's opened (M6): installed skills for any member; a place's skill for whoever can see that place; a personal skill only for its person.

Before, after, why

Before
  • A typed /name goes to the runtime as text; bundled commands work (T7).
  • The step shows a staged name and opens nothing (T8).
After
  • A picked skill is a validated field; typed text is never a command.
  • The step names the skill and version, and opens what ran, to whoever may see it.
Why a field and a table: the field keeps the person's words untouched and lets the site check them against this turn's staging. The table is the only place that knows staged name → identity → fingerprint at the moment the run used it.
