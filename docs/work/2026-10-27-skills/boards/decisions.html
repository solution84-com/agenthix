Questions and decisions

The questions raised while designing, how each was decided, and the defaults the design applies. The spec is written from these boards.

Status

  • Goal: at release, a person can find, give, use and look after their agents' skills, and can see when an agent used one.
  • How the boards work: the architecture boards are numbered 1–8. The UI boards are grouped by where people meet them (S, A, C, R). Each side feeds the other. A UI board that needs something new adds it to an architecture board, and an architecture choice shows up in the UI boards it touches.
  • Board 4, The model, is redrawn from everything decided (27 Oct). Next: the spec is corrected in place, then the UI boards.
  • Drawn so far: this page, 1 Today, and 2 Where a skill can live (being discussed). 3 Installing. Board 4, The model, is withdrawn and will be redrawn from 2 and 3. Boards not yet drawn are greyed out on the left.
  • Source: the draft spec, docs/work/2026-10-27-skills/spec.md. It is corrected in place as decisions land.

Decided

DecisionWhen
D1Skills get a unit of work of their own, for the release. The broader work on every asset an organisation owns and publishes stays separate, and skills are its first local consumer. The unit holds the whole vision, and what ships for the release is cut after the design.27 Oct
D2Revised by D20. Was: Skill management first. Agents and templates are out of scope unless moving them onto the same shape is easy. Anything reshaped for them is not surfaced until it is tested. Before the first release candidate nothing is carried forward, so moving them is a question of code, never of data.27 Oct
D3Out of scope: publishing between organisations (publisher identity, signatures, a registry, verification) and a marketplace.27 Oct
D5Map where a skill can live before choosing a model. Owning a skill (the organisation, always) is a separate question from where it is kept (platform, organisation, agent, place, workspace). The first model proposal mixed the two up and is withdrawn.27 Oct
D6Built-in skills stay, beside platform knowledge. A skill is written for the agent: it tells it directly what to do. The guide is written about the platform, for people and agents alike. They work hand in hand. A built-in ships with hq and updates with it, so it can't go stale. To keep duplication small, a built-in gives the steps and points to guide pages for what things are, rather than describing the product again. This narrows adr-0149, which rejected a platform skill as a second description of the product. A decision record is needed. (Q11, Q13)27 Oct
D7Agenthix isn't prescriptive about where a skill comes from. A skill can be installed from anywhere, through one open protocol, without tying anyone to Agenthix's service. A signed package shows who signed it. An unsigned one is allowed after a clear warning. (Owner, building on Q15 and Q16.)27 Oct
D8The install protocol (board 2d): the package ZIP, a fingerprint over its files, a Sigstore bundle signature (keyless or with a key), and four states. A signed package from a trusted publisher installs. One from a new publisher asks whether to trust it. An unsigned one is allowed after a warning. A tampered one is refused. Agenthix vouches that a signer is who they say they are, never that a skill is safe. The person installing is always asked about the two things that matter: unsigned, or who signed it. (Q17)27 Oct
D9An organisation signs.
  • Its release workflow, keyless (W1), is the recommended way: no keys to lose, a public record, and the same verifier as the platform's images.
  • Its own key (W2) is for offline use or to stay out of the public log.
  • A person's own signature (W3) is accepted, because refusing it would only push them to unsigned, but it is labelled as a person.
  • Never both (W4): who inside an organisation released something stays internal.
The organisation signs because it outlives its people: trust doesn't reset when a maintainer leaves. hq shows exactly what a signature proves (a repository and workflow, or a key), the administrator names the publisher when trusting it, and "Verified organisation" is kept for a hosted registry's later check. (Q18)		27 Oct
D10Every package is self-contained; installing de-duplicates by identity (I1–I6). There are no references between packages, for anyone. Each skill keeps publisher/name and a version. The same version is reused, a newer one is offered, and an older one leaves the installed skill alone. The same name from a different signer is a different skill. Agenthix's build copies each skill from one source, ending the hand-kept copies. (Q14)27 Oct
D11Installed skills are pinned, one version per organisation (V1–V6). Installing pins the version. Upgrade and roll back are explicit, and any version can be installed on purpose. Sites cache by fingerprint, as they already do. Different versions side by side come later. This holds for installed skills only; skills in files are observed, not controlled (F1–F5). (Q19)27 Oct
D12The organisation's installed version wins over a skill in files with the same identity. The file copy is set aside and shown as such. A person can't override it, though renaming the skill makes it a different skill, which is a deliberate choice. (Q20)27 Oct
D13Skills in files: files stay the store; hq lists them, installs into them and switches them. The organisation's default, Skills found in files, is On by default, Off by default or Never, with Off by default recommended. A place may choose a stricter default, never a looser one. Each skill has its own switch, with All on and All off for the page and for each group. (Q21, settles Q10 as B and Q3. Amended the same day: on or off by default, as two starting points, and a place's stricter default)27 Oct
D14Settled by the decisions above, listed so you can object:
  • Q9: yes, a workspace's repository skills are read, in all three folders teams use (.agents/skills, .claude/skills, .github/skills), under D13's controls.
  • Q12: the sort of what Agenthix ships stands. There are 2 built-ins, Kernel's 3, and 17 offered, and templates keep their role skills inside (D10). Template copies come from one source in the build.
  • Q15, Q16: Agenthix runs the only registry, later, as a hosted service. hq installs from any source and never publishes (D7, D8).
  • Q5: a new organisation installs no offered skills by itself. Built-ins are on, and templates bring what they need (R1).
27 Oct
D15A person's skills follow them into their own conversations everywhere, projects included. People bring their own way of working to a project and apply it within the project's procedures and standards.
  • Where they live: Your space's files.
  • How they arrive: hq delivers the turned-on ones by fingerprint, across sites.
  • Where they don't apply: runs other people start, and scheduled or automated runs.
  • Organisation setting: Personal skills outside Your space, on by default.
  • Safe: a skill adds no capability, and the conversation stays within the person's access (adr-0152).
On a clash, the organisation's installed version wins (D12). Between a person's and a project's skill, see Q22. (Q8)		27 Oct
D16The project wins over the person for the same skill. A person's way of working adds to the project's. To change how the project works, they write a skill that complements the project's, or update the project's knowledge or memory. The order for the same identity is: installed, then the project, then the person. (Q22)27 Oct
D17Maintainers are in this unit. An administrator names members as maintainers of an installed skill.
  • A maintainer may: edit it, accept an update, roll back, and review proposals for it.
  • A maintainer may not: install, remove, or choose which agents get it. Those stay with administrators.
  • When a member leaves: their assignments are dropped, and the skill's history still names them.
Every role and action pair gets a test, since this decides who changes what agents follow. If the release cut moves it out, it is recorded for later work. (Q4)		27 Oct
D18Editing an installed skill makes the organisation's own copy. For example, fernhill/code-review, made here.
  • The copy takes the original's place for the agents that had it. The original stays installed but set aside, one click to switch back.
  • A newer upstream version shows on the copy as news, with what changed, and is never merged automatically.
  • Skills the organisation made itself are edited in place, with history.
(Q23)		27 Oct
D19Provenance: a dated "based on" list in the package's manifest (basedOn), written once when a copy is made and never changed.
  • A copy inherits its original's list and adds the original as one line: identity, version, fingerprint, date, recorded: hq.
  • Editing never touches the list. hq's editor edits the skill, never the manifest.
  • People can only add stated credits for sources hq never saw.
  • A line is shown as verified where hq can match the original's fingerprint, and as stated otherwise.
  • The licence is carried forward and shown.
  • Removing a line outside hq is on whoever does it.
Credit is recorded and shown, never required or certified. (Q24)		27 Oct
D20One asset layer for every package kind, built in this unit. The kinds are skills, agent templates, board templates and team templates. Identity, the install check, provenance, pinning, update and roll back, history, maintainers and own copies on edit apply to every library item. Agents, boards and teams already made from a template are their own definitions and are untouched (adr-0072). Skills in files, switches and the person's skills stay skills-only. The work is ordered so skills become usable first: (1) the layer with skills; (2) templates on the layer; (3) screens and walkthrough. If the cut has to move step 2, it moves whole. Why now: before 0.1.0-rc.1 nothing is carried forward, so it costs only the build; after it, every reshape needs migrations. Revises D2. (Q6)27 Oct
D21Where it lives.
  • The Library moves into the main sidebar and is the single home for every installed asset, by kind (Skills, Agents, Boards, Teams). It holds updates, history, maintainers, provenance, and Add from any source.
  • Each place, a project and Your space, gets a Skills page for the skills in its files and workspaces, with switches. Your space's page also holds the person's own skills that follow them.
  • Each agent's page lists everything it will see, by level, with anything set aside and why.

D23"Has", not "given to". Ada has Code Review. On a skill's page the heading is Agents with this skill, with Add to agents… and Remove from Ada. On an agent's page: Ada has 9 skills.27 Oct
D24Editing a Library asset: draft, then publish. Agents draft, people publish, as with propose_workflow.
  • Edit makes a draft that no agent sees.
  • Publish asks for a note and makes the next version. Every agent with it gets it on its next turn, and roll back stays one click.
  • Ask an agent to edit opens a conversation with the skill attached. The agent's propose_skill edit lands as the person's own draft if they can edit that skill, or as a proposal for review if they can't.
  • Editing a skill another publisher signed drafts the organisation's own copy (D18).
27 Oct
D25The editor (U3b):
  • CodeMirror 6 in ui/ for every text file (EQ1).
  • One diff component for every "what changed", as a renderer behind the file frame's boundary (EQ2), in a single column (EQ3).
  • One draft per Library skill, shared: editing is collaboration. That's the stance unless much feedback says otherwise (EQ4).
  • Skills in a place's files are versioned by publishing too (EQ5, FV1–FV6). hq keeps the draft. Publish writes the files and records the version, which is also written into the skill's metadata. A change made outside the editor shows as changed in files, not published, with publish it or put back. A workspace's repository skills stay read-only.
  • Limits: staging's bounds, and text over 1 MB read-only (EQ6).
27 Oct
D26UI calls from the boards, 27 Oct:
  • Unsigned installs need an "I've read it" tick (A1).
  • Content of every published version, and of every version a run used, is kept as long as the run's record, and cached in both hq and sites for fast retrieval. Sites already cache by fingerprint (V5); hq keeps the content (A4).
  • The Library is one view of every asset, searched, with a filter by type (skills, agents, boards, teams) instead of tabs. Marketplace is a button that opens its own page, behind a feature flag: on in development only, off in production, refused where it runs (adr-0116), until it is built later (A6).
  • Sidebar order: Home, Chat, Your space, Projects, Tasks, Agents, Library. Tasks is used more often than Agents or the Library, so Tasks moves before Agents (A7).
27 Oct
D27Maintainers at three levels, and proposals go to the maintainers of the level they aim at.
  • One Library asset: its maintainers, named by an administrator (D17). They edit and publish it, accept updates, roll back, and review edits proposed to it.
  • The Library as a whole: Library maintainers, named by an administrator. They have the same powers for every asset, plus creating new skills and reviewing proposed new ones. Installing from outside (unless P3 allows it), removing, and choosing which agents have a skill stay with administrators.
  • A project's skills: amended the same day: no project skill maintainers. Project skills are files, so anyone with write access edits them: members in the editor as a draft or directly in the files, and agents. Only the project's administrators publish, switch on and off, roll back, review proposals aimed at the project, and set its default. Viewers read. Each person sees their own skills there as a private group. Writing is open; publishing is the control.
  • Your space: the person.
A proposal aimed at the organisation goes to administrators and Library maintainers, plus the skill's own maintainers for an edit. One aimed at a project goes to its administrators. One aimed at the person goes to the person. A member's own New skill is a proposal, unless they maintain that level. Any member may propose. (A2, A3, A5)		27 Oct
D28One maintainer role: Library maintainer, an organisation role, because every Library asset belongs to the organisation. Administrators name Library maintainers in settings. They create, edit and publish every asset, accept updates, roll back and review proposals; installing from outside (unless P3), removing, choosing agents, trust and naming stay with administrators. There are no maintainers per asset, which replaces the per-asset half of D17 and D27. Reach is shown when someone is named (security review M1), and is an accepted risk. Maintainers per team or department, like a department's process specialist, may come later.27 Oct
D29Instructions, skills and knowledge.
  • Instructions always steer.
  • A skill steers one kind of task, explicitly: it instructs.
  • Knowledge informs, and doesn't steer by itself: policies, guidance, processes, reference.
Processes are where skills and knowledge overlap. A process lives in knowledge, and a skill enforces it, as instructions or a skill enforce a policy. The user guide and the built-in skill-creator teach this rule.		27 Oct
D30Going back a version stays open (security review M4). Administrators and Library maintainers may install any version, newer or older, after a confirmation. The history records who, when and why, and that record is the main safeguard: the Library's people are trusted and accountable. Versions compare as SemVer. A withdrawn version gets a warning, not a refusal, which guards against mistakes. Agenthix's withdrawn versions ship in hq's image.27 Oct
D31An agent's publish always goes through a person's approval, with no permission switch (B1, YQ3). An agent may ask to publish, roll back, switch a skill on, or install. Each such call becomes an approval card for the person the agent acts for, and runs only when that person approves it. The person must hold the right at that level. The history records the person as publisher, "requested by Ada". No agent setting skips this gate, Bypassed included: today a bypassed agent runs even tools set to Never, which is why a plain refusal isn't enough. Trust settings and naming Library maintainers have no agent tool at all.27 Oct
D32An organisation administrator doesn't act inside a project's skills they don't administer (B2, YQ7). They govern through the organisation's default (on, off, never).27 Oct
D4The local half of organisation ownership comes in, applied to skills: the organisation owns every skill, maintainers look after them, there is a history of who changed what, all of it works on the organisation's own hq, and installing grants no capability.27 Oct
