U3b · Making and editing a skill

A skill can be a folder of files: SKILL.md, plus scripts, references, templates and assets. So making and editing one works like a small file explorer, with three modes: View, Edit and Changes. A person edits, or asks an agent to. Nothing reaches an agent until a person publishes (D24).

Today, numbered

  1. One file only. A skill is edited as its SKILL.md in MdFileEditor (hq/src/shared/components/MdFileEditor.tsx): the header and the body, in sections. Its other files can't be seen or changed in hq.
  2. New skill is a name and nothing else, on the agent's page or in the Library's dialog. It saves straight away, live for that agent.
  3. No changes view. An edit replaces the file. Nothing shows what changed, and there's no diff anywhere in hq: the git diffs on the seeing-the-work boards were stretch work, not built.
  4. What exists to reuse: the Files explorer's tree (hq/src/storage/pages/FolderTree.tsx) and the file frame with its renderers for Markdown, code, text, JSON, tables, images and PDF (ui/src/files/). The renderer boundary was designed to take diffs later.

The change markers

MarkerMeansShown as
AAdded: new in the draftThe letter A in the success colour, with +n lines
MModifiedThe letter M in the warning colour (amber, as in VS Code and most editors), with +n −m
✕DeletedA cross in the danger colour, and the name struck through
RRenamed or movedThe letter R in the accent colour, with the old name: style.md ← voice.md. Renamed and changed shows R, plus +n −m

Never colour alone: each marker has its letter or cross, and its name for screen readers ("modified, 3 lines added, 1 removed"). Colours come from the design tokens (--color-success, --color-warning, --color-danger, --color-accent).

  • Per file, as a git diff reads: unchanged lines for context, removed lines marked −, added lines +, old and new line numbers. All the draft's changes can be read in one long list, or one file at a time from the tree.
  • Compared with: the version in use, by default. The same view shows what changed in an update (U5), in a proposal (R1, C3), and in a file skill since it was switched on (P1). That's one component for every "what changed" in this design.
  • Undo per file, and Restore for a deleted one.

5 · Publish

The dialog lists the files changed, with their markers, and asks for a note: "Publish version 4: 4 files changed. Ada and Priya use it from their next turn." A new skill's first publish is version 1, and then offers Add to agents… (D23).

6 · A skill in a place's files: versioned by publishing too

Raised 27 Oct: files have no versions, but the skill itself should. Publishing is what versions it, in a place as in the Library.

RuleMechanism
FV1The same editor, the same draft and publishThe draft is kept by hq, never in the place's live folder, so no agent sees it. Publish writes the files into files/.agents/…/skills/<name>/ through the site, as writing in Files does
FV2Publishing gives it a versionhq records version → fingerprint → content for that place's skill, and writes the number into the skill's own metadata (version: "4"), so it travels with the files
FV3History and roll backFrom hq's record (A4 keeps the content). Roll back writes the older version's files back and publishes them as the next version
FV4Changed outside the editor: an agent's file tools, Files, or anyone writing the folderThe site reports a fingerprint hq didn't publish. The page shows Changed in files, not published, with Changes against the last version and two actions: Publish as version 5 or Put back version 4. Under Off by default it's off until then (D13)
FV5Your spaceThe same, with the person as the one who publishes
FV6A workspace's repositoryRead-only here. Its versions are its commits, and the repository decides what it holds
