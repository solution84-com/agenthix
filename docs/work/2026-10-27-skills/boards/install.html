The question: the file levels (L4–L6)

For L1–L3, hq already has actions: install, add, remove. For L4–L6 the store is files, which anyone who can write the place can change, agents included. Three ways to handle them:

A · Files only (today)
  • How: people manage skills by browsing and editing files. hq shows nothing more.
  • For: nothing to build. It's how Claude Code's project skills work.
  • Against: a person can't tell which skills an agent will see in a place. An agent-written skill is live at once with no one noticing. Nothing can be offered as an update. People must know the folder names.
B · Files stay the store; hq lists them and installs into them (recommended)
  • Listed: the site scans the place's skill folders (L4, L5, and L6 for each workspace) and reports each skill with its fingerprint. hq shows them on the place's Skills page, grouped by level, like Claude Code's /skills.
  • On or off: kept in hq per place. A skill found but never looked at is new. Whether new and changed skills start on or off is Q3, the trust question.
  • Install: Add to this project (or to one agent here) copies a skill from the platform's or the organisation's skills into files/.agents/…/skills/<name>/. It writes the origin into the skill's metadata, the specification's own key, so an update can be offered later.
  • Remove: from the page. hq asks the site to delete the folder. For a workspace it can't, because the repository owns it, so it is switched off instead.
  • Files still work: a folder someone drops in, or a repository brings, simply appears in the list. Nothing breaks for teams who manage skills in git.
C · hq installs; files are hq's alone
  • How: place skills exist only when installed through hq, which keeps a record. Folders written by hand or by a repository are ignored.
  • For: full control and a clean record.
  • Against: breaks L6. A team's repository skills, the reason to read workspaces at all, would never work. Agents can't write skills even when asked.

Proposed with B

Every way in ends in a list a person can see, with an on/off state kept by hq. The run stages only what is on.

Controls for skills in files: two layers

hq can read the place's files and its workspaces' repositories, so it can list every skill there (B above). The controls sit on that list.

LayerWhoChoices
C1The organisation's default: one setting, Skills found in filesAdministratorsOn by default: every skill found runs, and anyone can switch one off. Off by default (recommended): every skill found is listed but stays off until someone switches it on, and a changed one goes off again. Never: hq doesn't read skills from files at all
C1bA place's default: the same choice for one project, or for Your spaceThe project's administrator, or the person in their own spaceIt can only be stricter than the organisation's: a project can choose off by default when the organisation has on, never the other way. That's the same rule as every other override (adr-0072)
C2Each skill's switch, on the place's Skills page, grouped by where it was found (the place, one agent, each workspace). All on and All off for the whole page and for each groupThe project's administrator, or the person in their own spaceOn or off, remembered by fingerprint
Two starting points, as you'd expect: everything on, switch off what you don't want; or everything off, switch on what you do. The organisation picks one, a place may pick the stricter one, and All on and All off make either quick to change. A separate switch per workspace isn't needed: All off on that workspace's group does it. It's the same shape as Claude Code, where managed settings set the policy and per-skill overrides do the rest. The organisation's installed version still wins for the same identity (D12), whatever the switches say. Renaming a skill in files makes it a different skill. That's a deliberate choice, and the switches above still apply to it.
