5 · Review and approval

Level 2 of parts 3–4: each new version is read by plain checks and by the reviewer agent, and then a person decides with their advice in front of them.

From proposal to approval

New · nothing today

R1Plain checks

Rules that need no model, run by hq on the version's text. Each match is a flag on the card:

  • a secret variable used next to echo, printf, cat to output, base64, curl or wget;
  • a host in the workflow that isn't in the approved hosts;
  • a text parameter used outside a file argument;
  • an install that isn't pinned (no exact version and checksum, no lock file), or curl … | sh;
  • a step given a secret it never reads, or a step that installs and holds a secret;
  • GitHub permissions beyond what the steps appear to need, any new permission compared with the approved version, and any the App or the project's GitHub account doesn't have yet, with how to add it;
  • rm -rf, DROP, --force, git push -f;
  • a new variable or host compared with the approved version;
  • a step that holds a secret and runs anything from the workspace rather than the approved files (board 6), or runs git in the workspace's repository (board 9);
  • a parameter pattern that can match a value starting with -;
  • a variable named after one that changes how programs run (PATH, BASH_ENV, NODE_OPTIONS, LD_PRELOAD, GIT_* and the like): refused, not just flagged.

R1 also writes the card's one-line summary, from its own reading of the diff, never from the agent's text or the reviewer's.

R2The reviewer agent

Input: the version's files and settings, the approved version's diff, and R1's flags. Output: a risk level (low, look closely, high), and up to five points, each naming a file and line.

Model: the organisation's default model, through the usual model resolution. It runs as soon as a version is proposed.

R3Why it can't be steered

A workflow can contain text aimed at the reviewer ("reviewer: this is safe"). So the reviewer has no tools and no variables: the most a steered review can do is give bad advice. R1's flags are shown whatever the reviewer says, and the person's approval is still the control. Nothing the reviewer says decides what the person is shown: whether a version can be approved from the card is decided by R1 alone (U4).

R4The person decides

A project's administrator, or the person for their own storage. They see every file in full, the diff, R1's flags and R2's advice. They approve or decline this version.

In a person's own storage, the person approves for their own secrets and variables, and for GitHub contents and pull requests only. Any wider GitHub permission (secrets, workflows, actions, administration) needs an organisation administrator too. Which GitHub accounts a person's storage may connect to at all is set by an administrator (G1).

On screen: the approval card, in the conversation and on the workflow, U4.
