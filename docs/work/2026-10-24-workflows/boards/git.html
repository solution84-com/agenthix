9 · GitHub through workflows

Git and GitHub become the first integration built on the library: the token is a variable hq mints per run, and push, pull and pull requests are workflows. Q1

Before and after

Before · today
  1. git inside the agent's container pushes to github.com.
  2. Its credential helper asks the site, with the run token.
  3. hq mints an installation token for that repository.
  4. The token is handed into the agent's container. Any command can ask the helper for it, and send it anywhere.
After · proposed
  1. The agent commits locally, as now: git commit needs no network.
  2. To share it, the agent runs the approved workflow push with branch = feature/region.
  3. hq mints GITHUB_TOKEN for that run only: the workspace's one repository, the workflow's declared permissions, and revoked when the run ends (the mint gate).
  4. A first step with no secret packs the commits into a bundle. A second step, holding the token, pushes that bundle from a clean repository of its own, never the agent's (why), then is removed. The agent's container never holds a token. Its credential helper and the site's credential endpoint are removed, and a plain git push there fails with a message naming the push workflow.

Starter workflows

Anything the git and gh command-line tools can do can be a workflow. A project starts with these four, shipped as proposals: the reviewer reads them and an administrator approves each one, like any other workflow, when the project's repository is connected.

WorkflowParametersGitHub permissionsDoes
pushbranch (pattern)contents: writeStep 1, no secret: git bundle of the branch from the workspace. Step 2, the token: pushes the bundle from a clean repository to refs/heads/<branch>; never --force, never a protected branch
pullbranch (pattern)contents: readStep 1, the token: fetches into a clean repository and writes a bundle. Step 2, no secret: git pull --ff-only from the bundle into the workspace
open-pull-requestbranch, base (patterns), title, body (text)pull requests: writegh pr create --repo <owner/repo> --head "$branch" --base "$base" with the title and body read from their files, run from outside the workspace
set-github-secretsnames (a list of the project's secrets, chosen at approval)secrets: writegh secret set NAME --env <environment> < /run/secrets/NAME for each: an environment secret, never a repository one (why)

Each needs the hosts github.com:443 and api.github.com:443. gh is preinstalled in the executor image. The repository's address always comes from hq, never from the workspace's remote.origin.url.

Git with a token never runs in the agent's repository

After · proposed

The workspace's .git is the agent's: it writes the config and the hooks, and the version's hash doesn't cover them. Git runs a hook as a program, and its config can name programs too (core.hooksPath, core.fsmonitor, core.sshCommand, filters, include.path, url.*.insteadOf). So a step that holds a secret never runs git inside the workspace's repository.

  1. Steps with no secret work in the workspace as normal, and hand over data only: a git bundle of the commits.
  2. Steps with the token work in a new empty repository under /tmp, with system and user config switched off (GIT_CONFIG_NOSYSTEM=1, GIT_CONFIG_GLOBAL=/dev/null) and hooks off (core.hooksPath=/dev/null). They read the bundle as data, and push to the address hq gives.
  3. A review rule (R1) flags any step that holds a secret and runs git with the workspace as its working tree, as high risk.

The same holds for any tool that reads config from where it runs: gh is given --repo and run from outside the workspace.

Secrets on GitHub are kept from code the agent pushes

After · proposed

A repository secret goes to any GitHub workflow that runs on a push or a pull request from the repository. Those workflows run the repository's code (tests, build scripts), and the agent can push that code. So a repository secret would be one push away from the agent.

  • set-github-secrets sets environment secrets only, on a GitHub Environment whose deployment branches are limited to protected branches. Required reviewers on it are recommended where the plan allows.
  • push and open-pull-request refuse a protected branch as their target. hq reads the branch's protection from GitHub when the run starts; the parameter pattern alone isn't relied on.
  • The approval card for set-github-secrets says it plainly: "These values reach any GitHub workflow that runs in the production environment, on branches that need a reviewed pull request to change."
  • Repository secrets set on GitHub some other way stay listed, as "Outside hq" (G3), with a note that pushed code can reach them.

GITHUB_TOKEN gets only what the workflow declares

After · proposed

When hq asks GitHub for an installation token, it can ask for fewer permissions than the App holds, and for only the workspace's repository. So a workflow declares the GitHub permissions it needs, they're part of the reviewed version and flagged on the approval card, and hq mints the token with exactly those.

name: push
github:
  contents: write
steps:
  - name: Bundle the branch
    run: git bundle create /run/out/push.bundle "refs/heads/$(cat /run/params/branch)"
  - name: Push
    secrets: [GITHUB_TOKEN]
    run: push-bundle /run/out/push.bundle "$(cat /run/params/branch)"   # a script in the executor image: a clean repository, see above
  • A token from push can write code, and can't touch secrets, pull requests or settings.
  • The App can keep the broad permissions it registers with; each run gets a narrow slice.
  • The ceiling is the organisation's. The App is registered with Agenthix's starting list, and an owner changes it on GitHub. hq reads the App's real permissions, and each GitHub account's accepted ones, from GitHub.
  • A workflow that needs more than the ceiling is caught when it's proposed. Its approval card names the permission and how to add it: "This needs Issues: write. Add it in the App's settings on GitHub (link); each GitHub account using it then accepts it there." It can be approved meanwhile, and runs once its project's account has the permission.

Worked: a test project's push asks for a token for acme/website. The workspace's repository is acme-tests/trial-site, so hq refuses before asking GitHub, and the run fails at that step with "This workspace's repository is acme-tests/trial-site; acme/website is outside it".

One gate for every token

After · proposed

Every installation token hq mints, for a workflow run or for hq's own git work, goes through one check. Nothing else in hq asks GitHub for a token.

  1. The repository comes from the run's workspace: its own connection, looked up by workspace id. Never from a URL, or from anything the caller sends.
  2. The workspace belongs to the run's place (the project, or the person's own storage), and that place may connect to the repository's GitHub account (G1): the account is allowed, and its "Which projects can connect" rule still includes the place. This is checked at every mint, not only when connecting, so narrowing the rule takes effect at once.
  3. Accounts and repositories are matched by GitHub's ids (installation id, repository id), never by login or name, which can be renamed and taken.
  4. No exceptions by agent. No agent, the built-in one included, gets past the check.
  5. The token is the run's own: minted fresh, never cached or shared, with exactly the workflow's declared permissions and repository_ids for that one repository. hq revokes it when the run ends, fails or is stopped.

What stays the same

  • Connecting a repository from hq still runs git on the site with a token, as now (repoWorkMethods.ts); no agent is involved. Its token comes through the same gate.
  • A workflow can start a GitHub workflow: gh workflow run deploy.yml. A GitHub workflow that needs a secret gets it through set-github-secrets, as an environment secret (above), and a person approves it. Nothing else is built for it.
