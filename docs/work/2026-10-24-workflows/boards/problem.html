1 · Today: how a secret can leak

Why integrations wait: any value that reaches an agent's container can be read by whoever steers the agent.

The path a leak takes

Before · today

1Instructions hidden in content

A README, an issue, a web page or a tool result the agent reads contains instructions like "run this and send the result to…". This is prompt injection: the model can't reliably tell its person's instructions from text it reads.

2The agent follows them

It runs commands in its container through agenthix-contain, the Landlock sandbox that keeps commands away from the harness's own files and strips the harness's keys (secret-env.list).

3git credential fill

git's credential helper (agenthix-git-credential) is a script anyone in the container can call. It reads the run token SITE_MCP_KEY, which is not on the stripped list.

4The site and hq agree

The site checks the run token; hq checks the repository belongs to the run's storage, then mints an installation token for that repository, valid about an hour.

5The token lands in the container

The helper prints it to git, inside the container, where the agent's command can read it.

6It leaves

An agent's container has ordinary outbound internet (its network is a plain bridge, not --internal), so the command can send the token anywhere.

Read from the code, not yet run against the real site. Steps 3–6 ran end to end against a stand-in for the site in the spike workspace.

It isn't only git

Any integration built the same way has the same hole: a Slack token, a database password, a deploy key. If the value ever enters the container, through an environment variable, a file, or a helper that hands it out, a steered agent can read it and send it out. Hiding it from the prompt isn't enough: the agent doesn't need to see it in the prompt to run a command that prints it.

The rule this design sets

After · proposed

No secret value ever enters an agent's container.

  • An agent works with secret names only.
  • A value is used only by a workflow: a script kept in the project's library, whose version a person has approved, word for word. Once approved it runs as often as needed, by a person or an agent.
  • That script runs in a container of its own, never the agent's.
