2 · The design at a glance

Level 1: six parts. A project keeps a library of workflows, like the GitHub workflows a repository keeps. Agents write them, a person approves each version once, and then anyone in the project, agents included, can run it as often as they need.

The six parts

After · proposed

1Agent

Does: writes or changes a workflow, proposes it, and runs workflows whenever its work needs them.

Holds: secret names only; variables' names and values. Cannot approve.

Tools: list_workflows, propose_workflow, run_workflow, served by the site's MCP server and forwarded to hq.

2hq: the library and the variables

The library: every workflow, each version, which version is approved, every run. Secrets and variables, kept apart, like GitHub's: Secret values are encrypted with hq's secret key (secretCrypto.ts) and never shown again.

Decides: who may approve, that the version run is the approved one.

Board 3 →

3Reviewer

What: a built-in agent that reads every proposed version before a person sees it, and writes its advice on the approval card.

Holds: nothing. No tools, no variables. It only advises.

Board 5 →

4Approver

Who: a project's administrators; the person, for their own storage. Never an agent.

Decides: approve this version, with the reviewer's advice in front of them.

Board 5 →

5Site

Does: starts the executor container, runs the egress proxy, masks secret values in the output and in any file the run changed.

Board 6 →

6Executor containers

What: a fresh container for each step, from the executor image, sharing the run's workspace. Each gets only the secrets its step names, as files in memory. No network unless hosts were approved.

A worked example

  1. Sam's project has a secret variable STAGING_DEPLOY_KEY, typed in by Sam, an administrator, and a plain one STAGING_HOST. Its GitHub repository gives it GITHUB_TOKEN without anyone typing anything: hq mints it for each run (board 3).
  2. The agent needs to deploy to staging. There's no such workflow yet, so it writes deploy-staging and proposes it.
  3. The reviewer reads it: low risk; uses STAGING_DEPLOY_KEY only with ssh to STAGING_HOST; prints nothing secret. Sam reads the card and approves.
  4. From then on the agent runs deploy-staging whenever its work is ready, as often as needed, with no one asked. So can Sam, from the Workflows section.
  5. Next month the agent changes the workflow to also restart a worker. That's a new version: the reviewer reads it, Sam approves it. Until then the old version keeps running.
