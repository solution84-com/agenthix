  1. The same columns on both tabs: name and description, value, used by, changed. For a secret the value column says only what kind it is (text, file, from GitHub), never the value.
  2. Used by lists the workflows whose approved version names it. A secret or variable no workflow names says "Not used".
  3. When it was last replaced, and its rotate-by date: Rotate by a week before, Overdue after.
  4. ⋯ holds Turn off what uses it, Delete, and the history (set, replaced, every run that used it). Never the value.
  5. "Also on GitHub" shows where it was set and when.

  1. The value is in plain sight, so a person can check it's right at a glance, and agents can read it too.
  2. A workflow names the variables it uses, like its secrets; each of its steps then reads them as environment variables: $STAGING_HOST.
  3. Only administrators add, edit or delete; every change is kept as old value → new value, with who and when.
  4. Saving a value that looks like a secret (a key's BEGIN line, a long random string, a token's known prefix such as ghp_) asks: "This looks like a secret. Add it under Secrets instead?"

Why

  • Two tabs, because they're handled differently: a variable is meant to be read and checked; a secret is meant never to be seen. Mixing them in one list invites a secret saved as a plain value.
  • The secret form asks the questions our own secret handling asks: what is it, what does it reach, where does a new one come from (board 4).
  • Revoking is one button, because the moment a secret may have leaked is the worst time to hunt for what uses it.
