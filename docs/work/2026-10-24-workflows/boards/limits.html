10 · What it stops, and what it does not

The spike's attack paths, each with what stops it. Every row becomes a test that plants dummy secrets and fails if one turns up where the agent can read it.

Each attack, and what stops it

AttackWhat stops it
A1The workflow prints or encodes a valueReview before it can run: plain checks flag it, the reviewer and the person read it; masking catches the plain forms
A2A dependency is swapped, or a package steals a secret while installingInstalls are pinned, from a lock file that is one of the workflow's own files, and only from approved hosts; a step that installs gets no secret unless it names one, and the plain checks flag a step that does both
A3A process from one step waits for a later step's secretEach executor container is removed before the next starts

A7The value is sent out, directly or by DNSNo network by default; with hosts approved, the proxy lets only those through, resolves names itself, answers the step's DNS, and refuses private addresses. Not a hosted service anyone can sign up to: see below

What it does not protect against

An approved workflow written to misuse a secret. If a person approves code that sends a value to an approved host, or uses it to do damage, it will. The design moves the risk from "any prompt can leak a secret" to "a person approved code that leaks it, after a reviewer and plain checks read it".
  • An approved host that takes anyone's data. github.com, registry.npmjs.org and the like accept data from any account, so allowing one doesn't stop a step sending a value to an account the attacker owns there. What stops it is that steps run only approved code, with the controls above (A13); the allow-list narrows where, it doesn't prevent.
  • What the secret itself allows. A run can do anything its secret permits. Narrow secrets (a database user with only a migration's rights, a deploy key for one server) stay the operator's job.
  • The agent's own outbound network. Unchanged by this unit. With no secret inside the agent's container there's nothing secret to send, but the agent can still send the workspace's files. Limiting that is a separate decision.

The decision record it needs

ADR-0037 chose GitHub Actions over a platform-owned runner (its option C) because building secret storage, injection and isolation ourselves was the risk. This design builds that runner, deliberately: it's the only way to keep every integration's secrets out of the agent's container, and it reaches what GitHub Actions can't (a database on the site's machine, a firewalled server). A new decision record amends ADR-0037. GitHub workflows stay, and a workflow can start one.

It also records a second reversal. ADR-0037 kept a real-secret run's output from the agent, because masking can't close that channel fully. Here the agent gets the masked output, so it can fix a failing deploy without a person relaying the log. What bounds it instead: a person approved the exact code, masking covers every secret of the place, and agent reruns are limited (board 3).
