6 · Running: a container for each step

Level 2 of parts 5–6. A workflow is a run like any other, on the agent's workspace, except that it can read secrets. It runs the approved files only, on a snapshot of the workspace the agent can't touch while it runs. Each step runs in a container of its own and gets only the secrets it names.

From run to result

New · nothing today
  1. Asked: the agent calls run_workflow("push", { branch: "feature/region" }), or a person presses Run.
  2. Checked by hq: the workflow is on; it has an approved version; every parameter matches its pattern or list; every secret it uses still exists. For a secret from an integration, hq mints the value now (for GITHUB_TOKEN, an installation token for the workspace's repository, through the mint gate on board 9).
  3. Sent: hq sends the site holding the project's storage a run instruction over the control channel (already encrypted and authenticated): the files, their hash, the workspace, each step's secrets, the workflow's variables, the parameters, the hosts and the limits.
  4. Checked again by the site: it recomputes the hash from the files it received, and refuses if it differs. It writes those files to a read-only folder, /run/workflow, outside the workspace.
  5. Snapshot: the site copies the run's workspace (copy-on-write where the disk allows). Every step works on this copy; the agent's container can't see or change it until the run ends (why).
  6. Each step, in order: the site starts a container for the step, with only that step's secrets, runs it, and removes it. The first step that fails ends the run.
  7. Ended: the site scans the output, and every file the run changed in the copy, for secret values (board 8). Only then are the changes written back to the agent's workspace, and the result sent back.

The executor containers, beside the agent's

AThe agent's container

Holds no secret at all once git goes through workflows (board 9). It shares nothing with the steps while they run: not the snapshot, not the network, not processes. It sees the run's changes only after they've been scanned. It now stands between an injected agent and the machine, so it gets the executor's hardening: --cap-drop ALL, no-new-privileges, and a read-only root apart from its own writable folders.

BAn executor container

Started by the site with docker run from the executor image, for one step, then removed with everything in it. No process from one step is still running when the next starts.

CThat step's values

A tmpfs with /run/secrets/<NAME> for only the secrets this step names, and /run/params. The variables the workflow names are its environment variables. A build step that names none gets none. Never on disk.

DThe egress proxy

On the site. A step's only route out, when hosts were approved. It lets through connections to those host:port pairs, resolves names itself, and refuses everything else. It tells runs apart by their network, never by source address, and the agent's container can't reach it. It refuses private, loopback and link-local addresses (the site, hq, a cloud's metadata address) unless that exact address was approved, and checks again after resolving the name. The step's DNS points at the proxy, so a lookup can't carry data out through Docker's own resolver.

EThe workspace snapshot

A copy of the run's workspace, taken when the run starts. Each step binds it at the agent's path, so paths work the same, and what one step builds the next one sees. Steps with no secret get it read-write. Steps that hold a secret get it read-only, plus /run/out, a scratch folder of the run's own for what they hand on. Only the workspace the run came from, not the agent's whole storage folder.

FThe approved files

/run/workflow, read-only, holding exactly the files the hash covers. run:, and every file a step names, is found there and nowhere else.

Why the run gets the approved files and a snapshot

After · proposed

A person approves one exact version. But the workspace is the agent's: it can change any file there, before the run and while it runs. If a step with a secret ran a script, a lock file, a git hook or a build output from the live workspace, it would run what the agent wrote, not what was approved.

  1. What runs is the approved files: run: and the files it names come from /run/workflow, which the hash covers. A run: ./deploy/upload.sh means the version's deploy/upload.sh, not the workspace's.
  2. Nothing changes under a run: steps work on a snapshot, so the agent can't swap a file between the hash check and a step, or between steps.
  3. What a secret step runs from the workspace is flagged. A step that holds a secret and runs anything from the snapshot (node_modules/.bin, dist/, a package.json script) runs code the agent could have changed before the run. The review flags it as high risk: "this step runs code the agent can change after approval". It can still be approved, but never from the card (board 5).
  4. Secret steps can't write into the workspace: they get the snapshot read-only, and hand on only through /run/out, which is scanned before anything leaves the run (board 8).
  5. Links are never followed. Wherever the site copies, snapshots, scans or writes back workspace files, it refuses to follow a symbolic or hard link, so a link can't point the site at a file outside the workspace. A version can't contain a link.

Writing back: the run's changes are applied to the workspace as a change set. A file the agent also changed during the run isn't overwritten: the run reports it as a conflict and keeps its own copy beside it.
