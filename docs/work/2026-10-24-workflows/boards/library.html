A version is all of that, frozen: hq copies the files' bytes (refusing links) and hashes everything (SHA-256 over each file's path and content, then the variables, parameters, hosts and time limit). Change anything and it's a new version, waiting for review and approval. The approved version runs any number of times, by a person or an agent, with no one asked again, until a newer version is approved.

  • What the hash covers: everything the run instruction carries, not only the files: each step's list of secrets, the GitHub permissions, the names set-github-secrets was approved for, the variables' names, the hosts, the parameters' patterns, the time limits and the executor image's digest. Encoded one way only (sorted, length-prefixed fields; paths normalised, with no ..), so two different versions can never hash the same.
  • An approval is of a version of one workflow in one place: stored as (workflow, project or person, hash), never as "this hash is approved". The same files proposed in another project wait for that project's own approval.
  • Agent reruns are limited: an agent can run an approved workflow at most 30 times an hour by default, which an administrator can change per workflow. People aren't limited. Past the limit, the run is refused and the agent is told why.

On and off

New · nothing today

Every workflow has a switch, like enabling and disabling a workflow on GitHub.

  • On: the approved version can be run, by a person from the Workflows section or by an agent with run_workflow.
  • Off: nobody can run it, person or agent. list_workflows still shows it to the agent, marked off, so the agent can say "deploy-staging is turned off" instead of trying something else.
  • Turning it back on needs no new approval: the same approved version runs again.
  • Who can switch it: the people who can approve it. An agent can't.
  • A workflow is on when its first version is approved. A run already going when it's turned off is stopped.

Parameters

Git and GitHub operations need values that change each run: a branch, a commit message, a pull request's title. So a workflow declares its parameters, and they're approved with it.

  • Each parameter has a name and either a pattern (a regular expression the whole value must match) or a fixed list of allowed values.
  • Values reach the workflow as files, /run/params/<name>, never pasted into its text, so a value can't become code.
  • hq refuses a run whose value doesn't match. Worked: branch = "feature/region" runs; branch = "--force" is refused, because the pattern's first character can't be -. The starter workflows also pass it as refs/heads/<branch> after --, so git never reads it as an option.
  • Free text (a commit message, a pull request's body) is allowed as a parameter marked text. The reviewer checks that the workflow only ever passes it as data, for example git commit -F /run/params/message.
