4 · Secret management

How a project's secrets are kept, described, scoped, rotated and revoked. The same principles we follow for our own secrets, built into the product.

The principles

After · proposed

S1One keeper

Every secret lives in one place: hq's secret store. It's encrypted at rest with AES-256-GCM under SECRETS_MASTER_KEY, which is held in hq's environment, not its database, so a copy of the database alone can't be read (secretCrypto.ts, used today for the GitHub App's key and model credentials). It's decrypted only in memory, only for a run. Each value is encrypted with its own secret's id and its place (project or person) as associated data, so a value copied into another row or project fails to decrypt instead of being used there. A file secret is stored and handed to the step as bytes, exactly as uploaded.

S2Never show a value

A value is typed once and never shown again: not in the page, not in a log, not to an administrator, never to an agent. It can only be replaced. Output and changed files are masked (board 8).

S3Every secret says what it is

Each one carries, in words: what it is, who issues it, what it lets a workflow do and how far it reaches, and where to get a new one. The name says what it's for: STAGING_DEPLOY_KEY, not SSH_KEY.

S4The narrowest scope

A secret belongs to one project, or to one person's own storage. Only an approved workflow version that names it gets it, and only for that run. The form asks for the narrowest credential that works (a deploy key for one server, a database user with a migration's rights).

S5Short-lived where possible

A value an integration can mint is minted per run and expires on its own: GITHUB_TOKEN is an installation token for the workspace's repository, minted for the run and revoked when it ends. Nothing to rotate, nothing stored. And it carries only the permissions the workflow declares: a token from push can write code and nothing else.

S6Rotation is planned

A stored secret can carry a rotate by date. A week before, the project's administrators get a notification; on the day, the Secrets tab shows it overdue. A replaced value is used from the next run on.

S7Revoking is one action

Each secret lists the workflows that use it. Turn off everything that uses it switches all of them off at once and stops any run in progress, for when a secret may have leaked. Then replace it at its issuer, and turn them back on.

S8Every use is recorded

Setting, replacing and deleting a secret, and every run that used it, with who and when. Never the value. If masking ever finds a value in a run's output, the run is flagged "printed a secret", and the administrators are told to rotate it.

Can changing a variable send a secret somewhere new? Not off the site's network: the hosts a step may reach are part of the approved version, so pointing STAGING_HOST at another server is refused by the egress proxy. Variables are still administrator-only, and every change is recorded.

A secret's journey

  1. Typed: by an administrator into the form; sent to hq over HTTPS.
  2. Stored: encrypted at once; the plain value is never written anywhere.
  3. Sent: decrypted in hq's memory only for a run of an approved version that names it; sent to the site over the control channel.
  4. Used: held in the site's memory, written to the executor container's tmpfs, gone when the container is removed.
  5. Never: in an agent's container, a log, a page, or a database other than hq's, encrypted.
