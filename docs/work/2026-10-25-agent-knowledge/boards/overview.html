2 · The design at a glance

Level 1. Three kinds of knowledge, one way to reach each, and one check at the edge of a place. Agents look things up when they need them; nothing is preloaded beyond a few lines saying where to look.

Four levels of knowledge, and what is not knowledge

WhatHoldsWritten byRead byReached through
Platform knowledge newHow Agenthix works: its words, where each screen and setting is, how to do things. Not about anything a customer builds.The maintainers, as the user guideEvery agent in every organisationsearch_knowledge and read_knowledge, as platform: pages. Board 3
Organisation knowledge newHow the whole organisation works: its processes, policies, brand, clients. Its own pagesOrganisation admins, and agents when an admin asksEvery member and every agent, in every projectThe same knowledge tools, scope: "org". Boards 4–5, U5
Project knowledgeA project's own knowledge: its workflows, decisions, conventions, reference, in detailThe project's people and its agentsThe project's members, and agents working in the projectSearch and read, as for the guide; save and edit through one gate. Boards 4–5
Personal knowledgeA person's own knowledge, in their own space and their personal projects: the same as a project'sThe person and agents in their spaceThe person and runs in their spaceSame as project knowledge
MemoryPreferences and what an agent learned while working. Rows in hq, recall/remember. Unchanged, except that recall no longer searches knowledge.
InstructionsA place's AGENTS.md and an agent's own instructions: read on every run. Unchanged.
PermissionsWhat a run may do is what its tools allow. Platform knowledge describes the product; it never grants anything.

The parts

After · proposed

1Agent

The lead (hq) or a worker (site). Starts with one short Knowledge section in its instructions saying where to look; nothing else is loaded.

2Platform knowledge

Built from docs/guide/ when hq's image is built, and searched and read as the platform: level of knowledge. Same commit as hq, so it never describes another version.

Board 3 →

3Knowledge tools

search_knowledge (a grep), read_knowledge, write_knowledge, edit_knowledge, delete_knowledge: hq operations, served to workers through the site's MCP server and to the lead as conversation tools. No place parameter: always the run's or the conversation's place.

Board 5 →

4A place's knowledge

The place's own guide, on the site, outside what runs mount: Markdown pages in any sections, with title, description, tags and any properties of the team's own. Every change goes through one gate, which keeps the previous page for 30 days.

Board 4 →

5The conversation's places

A conversation reaches its own place; any other place is added by the person, in its header, like Claude Code's additional directories. The lead may suggest one, never add it. The person sets the blast radius (board 6, C3).

Board 6 →

6The Knowledge tool

People list, read, edit, delete and restore pages, and see who changed what. Correcting by asking an agent works the same way, through the tools.

Boards U2–U4 →

A worked example

  1. Sam asks Kernel, in Your space: "where do I add a model key?" Kernel doesn't know the setting, so it calls search_knowledge("model.?key|api.?key|provider"), finds platform:your-tools/providers.md, and answers with a link to that settings screen in hq (board 3, C2).
  2. In the Website rebuild project, Sam says "release process is wrong: staging deploys need Mia's OK now". Kernel calls search_knowledge("release|deploy"), reads the page, and changes the one passage with edit_knowledge. The conversation shows "Updated page · Release process" with Undo (C1).
  3. Later a worker on a task in the same project calls search_knowledge("staging"), finds the page and follows it, with the same tool the lead used (board 5).
  4. Mia opens Knowledge › Release process, sees "Changed by Kernel, asked by Sam, 2 hours ago", and opens History to see the change (U4).
  5. From Your space, Sam asks Kernel to set the same release process up in Shop. Shop isn't in the conversation, so Kernel shows "Add a place to this conversation: Shop". Sam adds it; Kernel reads Shop's knowledge and starts the work there (C3).
