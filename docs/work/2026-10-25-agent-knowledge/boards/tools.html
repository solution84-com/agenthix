Three layers: file tools underneath, knowledge and guide on top

After · proposed

FFile tools: our own, universal

One module, @agenthix/core/file-tools, a new node-only subpath export beside ./host-crypto, lifted from the file tools Agenthix already owns for OpenCode (ADR-0085: the safe open-then-check, text reading, line-numbered reading, writing) and extended with ripgrep search. The OpenCode plugin builds on it too. Plain grep, read, write and edit, shaped like Claude Code's, over any folder they are given (the root). Nothing in them knows about knowledge, places or the guide.

  • grep(root, {pattern, path, glob, output_mode, -i, -n, -A/-B/-C, head_limit, offset}): runs ripgrep
  • read(root, {file, offset, limit}): numbered lines, and a version (a hash)
  • applyEdit(text, {old_string, new_string, replace_all}): the new text, or why not; exact match
  • write(root, {file, content}): written beside, then renamed in, so never half-written

The guards live here (board 3, S1–S8): paths kept inside the root, no links, rg without a shell, pattern after -e, time and size caps, fixed messages. So every user of the module gets them.

KKnowledge and guide tools

Thin wrappers that pick the root and add what is theirs:

  • search_knowledge = grep on each level's pages at once (the place's, the organisation's, the guide), merged, each hit marked with its level
  • read_knowledge = read on the level its name starts with
  • edit_knowledge = the gate: read → applyEdit → check the rules → keep the previous version → write → record who
  • write_knowledge = the gate, with the whole content
  • platform: pages: grep and read on the built guide in hq; changes refused

SServing

As drawn below: hq operations, given to workers through the site's MCP server and to the lead as conversation tools. hq answers a search by asking the place's site, the organisation's site and its own copy of the guide at once, and merges the results within one time limit. A read or a change goes to the one level the name names.

Why a universal layer: if Agenthix later runs agents in a runtime of its own, that runtime's file tools are these, on a workspace folder, already built and tested. Knowledge and the guide are simply their first users.

Rule
D1Search everything it may see, by default: every place in the conversation (or the run's one place), the organisation, the platform guide. scope (a place's key, org, platform) only narrows it.
D2Every hit is marked with where it is from (a place's key, org: or platform:), and that mark is the page's name for read_knowledge.
D3The most specific wins where pages differ: a place, then the organisation, then the platform guide. Results come in that order, the conversation's own place first. Two places that differ are both shown, each marked; the person's question says which is meant.
D4Links are followed from page to page, across levels (org: links from a project page).

The five tools: the native ones, on knowledge

Agents are trained on their harness's own Read, Grep, Write and Edit. These tools take the same parameters and behave the same way, so an agent already knows how to use them. Only the target differs: a page of knowledge, at any level, instead of a file.

  • Built on the file tools Agenthix already owns for OpenCode (ADR-0085, site/opencode-plugin/src/files/), lifted into core and extended: the knowledge tools take Claude Code's names, exact matching for edits, read-before-write enforced, and ripgrep for search; the plugin keeps OpenCode's shape on the same module.
  • No place parameter beyond what the person allowed. A worker's place comes from its capability token. The lead's places are the conversation's: its own and those the person added (C3). A page's name says its level; search_knowledge's optional scope narrows a search to one of them. Nothing can name a place outside them. Changes to org: pages refuse unless the run or turn acts for an organisation admin Q5; platform: pages are read-only.
  • A page is a name, not a file path, e.g. processes/release.md. The site resolves it inside the place's pages/ only, refusing .., absolute paths and links.
  • Moving a page is writing it at the new name and deleting the old; the Knowledge tool does both as one "Move" for people.
  • Change tools are offered to the lead only when the turn answers a person (as remember is), and to workers in runs that have write tools.
  • Served as hq operations: to workers through the site's MCP server, forwarded like the other tools; to the lead as conversation tools. hq asks the place's site through channel methods; searchKnowledge changes to take Grep's parameters and run ripgrep, under board 3's guards S1–S8 (the site's server image gains the ripgrep package); writeKnowledge, editKnowledge, deleteKnowledge, restoreKnowledge and knowledgeVersions are new: a new minor version of core/src/protocol/locationFiles.ts.

Exactly how the agent would change a file: find the line, read around it, replace the text. A few lines sent, not the page. A new decision record is one write_knowledge with the whole Markdown, the team's properties in its front matter, following the place's AGENTS.md.

What tells an agent how to write

The tools' descriptions, which every agent has, and the refusals, which say exactly what to fix:

write_knowledge — Works like Write, on a page of this place's knowledge. Content is the
whole page as Markdown. It must start with front matter: title, a one-sentence description,
up to 8 lower-case tags, and the place's own properties (status, date…) as its other pages
have them. Read an existing page with read_knowledge first. For part of a page, use
edit_knowledge. Change knowledge only when a person asks you to or corrects it.

edit_knowledge — Works like Edit, on a page of this place's knowledge: replaces old_string,
which must appear exactly once unless replace_all, with new_string.

The team's conventions (sections, naming, which properties a decision has) are its own, in its AGENTS.md, which every run already reads. The platform adds none.

recall stops searching knowledge.

Why

  • Reading as for the guide: search and read cover it, for every agent.
  • The native tools' shape: agents are trained on Read, Grep, Write and Edit, so the same parameters and behaviour mean they already know how to use these. Native tools on a mounted folder were weighed: nothing could refuse a bad change or see one made through bash, and the lead has no files.
  • Edit beside write: detailed pages change a passage at a time; sending the whole page for each would be slow and costly.
  • No drafts: each call is one finished change; versions are the undo.
  • No knowledge folder in runs: the tools are the one way in, as for the guide.
  • No list tool: an empty search gives the shape (sections and tags); a list of thousands of titles would only be cut short.
