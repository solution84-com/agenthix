4 · Knowledge: a place's own guide

Level 2. What a place's knowledge is, how it is stored, and the one gate every change goes through.

What knowledge holds

Four levels, one shape. The platform guide (board 3), the organisation's knowledge, a project's, and a person's (their own space and personal projects, which work exactly like a project). Organisation, project and person each have their own knowledge, stored and changed the same way.

Anything a project needs shared across its workspaces, written in as much detail as it needs: its processes and workflows, its decisions, its conventions, reference about the client or the domain. It is a place's own guide, the way the platform guide is Agenthix's. A person's own space has one too.

Kept here or elsewhere: the team choosesElsewhere, always
  • Processes and workflows: "How we release", "Onboarding a client"
  • Decision records (ADRs), if the team wants them here rather than in a repository
  • Conventions, glossaries, reference
  • What every run must read: the place's AGENTS.md
  • Preferences, and what an agent learned along the way: memory
  • Code and what belongs with it: the repository in a workspace
  • Files made or uploaded (PDFs, images): Files and artefacts, linked from a page

Not opinionated: the platform fixes only what it needs to list and search pages. How a team lays out its sections, names its pages and which properties it records are the team's, written down in its AGENTS.md if it wants agents to follow them.

The gate: every change, one way

After · proposed

G1A change arrives

From an agent's write_knowledge or edit_knowledge (board 5), or a person's editor in hq (U3). Each call is one finished change: there are no drafts.

G2Apply it

A write is the whole page. An edit replaces one passage, which must appear exactly once in the page as it is now; if the page changed so that it doesn't, the edit is refused and the current page comes back. A write carries the version it started from; a changed page refuses it the same way.

G3Check the result

Every change, from an agent or a person: rules T1–T4 on the page as it would be, so an edit that breaks the front matter is caught too. Anything wrong refuses the change with the problems in words: "description is missing"; "tag 'Deploys' must be lower-case"; "over 64 KB". Nothing is stored.

G4Swap it in

The site moves the current page into versions/ and renames the new one into place: one rename, so a reader never sees half a change.

G5Record who

hq records the change: place, page, created / edited / moved / deleted / restored, and who: a person, or an agent with the person it was answering and the conversation or run.

One set of rules, in one module in core, used by the site's gate, the site's itemiser and hq's editor, so the three cannot disagree.

Versions and pruning

After · proposed
  • A version is the whole earlier page, versions/<page>/<time>.md: a 10 KB page with 20 versions is 200 KB. Restore saves it back through the gate, as a new version.
  • Delete moves the page into versions/, marked deleted: Recently deleted, for 30 days.
  • Pruning, by a daily job on the site: a page's versions are kept 30 days, and its last 20 always; a deleted page 30 days. Each place's versions are capped at 200 MB, oldest first.
  • Delete permanently, for a page or one version (a pasted password, a person's details): removed at once.

The itemiser

After · proposed

The site's location.listKnowledge walks pages/ and returns sections and pages: title, description, tags, the team's properties, when it changed, and its problems against T1–T4. The gate means problems should not arise; the itemiser still checks, so a file put on the disk by hand shows with what is wrong instead of breaking the list. A page with problems still shows, titled from its file name.

Why

  • A place's own guide: detailed pages grouped in sections, the shape of the platform guide, so knowledge reads and works the same in both.
  • Not opinionated: free sections and the team's own properties let a team keep decisions, processes or anything else shared across its workspaces, or keep them in a repository instead.
  • Edit as well as save: changing one step of a detailed process sends a few lines, not the page.
  • One gate: the shape is checked before anything is stored, every change has an author and a previous version, and a change never lands half-done.
  • Versions are files, so pruning and permanent deletion are deleting files. (Git was weighed and rejected: pruning or removing something for good means rewriting history.)
