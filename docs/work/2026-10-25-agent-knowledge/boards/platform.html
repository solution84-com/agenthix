3 · Platform knowledge: from the guide to the agent

Level 2. The user guide is already written for each release, page by page, for people. Platform knowledge is that guide, plus a glossary, built into hq's image and read by every agent through the same search_knowledge and read_knowledge as every other level of knowledge, as platform: pages. Nothing is written twice.

Two places, one hand-off

Platform knowledge is made in our repository and CI, and used inside each organisation's hq. The only thing that crosses from one to the other is hq's image: an organisation never builds anything, and our CI never sees an organisation.

P3The tools reference new, generated

Written by the build from hq's tool registry (hq/src/shared/mcpTools.ts and the schemas beside it): each tool's name, what it does, and which kinds of run get it. Never written by hand, so it cannot disagree with the tools.

P4The build step new

No person runs it. It is a stage of hq's image, so whatever builds hq's image builds it:

  • A release: the rehearsal (scripts/release/prove.sh) and the Release build workflow; the tag only publishes what they built.
  • Development: hq's dev start runs it before hq boots.
  • Checks: its tests, in hq's unit suite.

Writes hq/assets/platform-guide/ (gitignored; layout below). Fails on a page without a description or a glossary that doesn't parse.

Two changes to our CI so this holds. hq's image parts in scripts/images/parts.json gain docs/guide/ as an input (today: core/, ui/, hq/), so a guide change makes a new key and a new image; and the change map behind scripts/affected.mjs sends a guide change to hq's checks. The Fleet Console already builds its Help from docs/guide/ the same way. hq's image also gains the ripgrep package (today only the agent and executor images have it).

The files P4 wrote, inside hq's image. hq reads them from its own disk to answer the tool; nothing is copied to sites or into runs. The platform package (hq/assets/platform/skills) is not used for this and stays as it is.

P6One more source for search_knowledge

No tools of its own. The guide is the platform: level of knowledge (board 5): search_knowledge searches it with the organisation's and the place's knowledge, marking its hits platform:your-tools/providers.md:12: …, and read_knowledge("platform:your-tools/providers.md") reads a page. hq runs both on its own copy, with the file tools (board 5, layer F). Read-only: a write, edit or delete on a platform: page is refused.

Every platform: result starts with "This describes Agenthix. What you may do here is what your tools allow."

P7Every agent reaches it the same way

Through search_knowledge and read_knowledge: workers through the site's MCP server, the lead as conversation tools. Nothing of an organisation is in the guide, so every run and every turn may read it.

Running a pattern safely

After · proposed

A pattern is written by a model, which may have read untrusted text, so it is treated as hostile input. What could go wrong, and what stops it:

\1
S1A pattern that never finishes (catastrophic backtracking, such as (a+)+$), freezing hqripgrep (rg), the program Claude Code's Grep runs. Its regex engine (Rust's regex) never backtracks: its time grows only in line with the text, by design. A pattern it can't run (backreferences, look-around) is refused with ripgrep's own message, which agents know from Grep.
S2Heavy or many searches slowing hq for everyonePattern at most 500 characters. rg runs as its own process, so hq never waits on it, killed after 2 seconds ("search took too long; narrow the pattern"). --max-filesize, --max-columns, one thread. At most 30 calls a minute for one run or conversation, then "too many searches; wait a moment".
S2bA pattern or option that takes over the command: a flag like --pre slipped in, or shell charactersrg is started directly, never through a shell. Its arguments are built only from the tool's allowed parameters; the pattern is passed after -e, so it can never be read as a flag; links are not followed; it runs inside the guide's folder only.
S3Reading something private through a pathSearch and read work only inside the built guide's folder in hq's image, read-only. A page name is resolved inside that folder and refused if it leaves it (../, absolute paths); links are not followed (the file tools' guards, board 5).
S4Something private in the guide itselfThe build takes only docs/guide/*.md (not README.md, the writers' rules) and the generated tools reference, all public in this repository. A test fails the build if anything else lands in platform-guide/. Nothing of an organisation is ever in it.
S5A huge result filling the model's contextThe caps in P6 (50 matches, 8,000 characters, 16,000 a page), each with "cut: narrow the pattern" or the next offset.
S6An error that gives the system away (stack traces, file paths, versions)Each failure is one of a fixed set of messages (S1, S2, S3, "the guide isn't available in this install"); nothing else is returned. Details go to hq's log.
S7A person's words kept in logs: a pattern may carry what the person saidhq's log records the call, its time and its outcome, never the pattern. The conversation shows the work step to the person, as it shows every tool call.
S8The tools breaking a turn or a runEvery failure is a normal tool result the model can act on, never an exception that ends the turn. If the built guide is missing (a dev hq that skipped the build), hq says so once at boot and the tools answer "the guide isn't available in this install".

The guide is public, so S2b–S4 protect against the tools becoming a way to read anything else, not against reading the guide.

How an agent knows to look

After · proposed

It doesn't have to choose: one search_knowledge covers the guide, the organisation and the place, and each hit says where it came from (board 5). The "MySpace" trigger sits in that tool's description, which every agent has:

search_knowledge — Works like Grep, over everything known here: how this place and this
organisation do things, and how Agenthix itself works (its words, screens and settings).
Each match says where it is from: place:, org: or platform:. Use it before asking how
something is done, and whenever a person names a place, screen or setting you don't
recognise, before asking them what they mean.

The full tool definitions are on board 5. The name "Agenthix" is written by the build from BRANDING.displayName (core/src/naming/branding.ts), so a rebrand changes one constant and the guide's text, no identifier (D17).

How it stays in step with the product

RiskWhat prevents it
The guide describes another version than the one runningBuilt from the same commit as hq's image, and served by that hq.
A site on another versionIrrelevant: the tool is answered by hq, not the site.
Tool documentation drifts from the toolsGenerated from the registry (P3); the existing schema drift test covers the registry itself.
A new screen ships without words for itThe guide's own rule already asks for its page; the glossary rule (P1) asks for its words. Checked in review, like the page.
A page goes out of dateThe same as for people: the guide's screenshots are regenerated each release and reviewed with them.

Why this shape

  • The guide is the one source because it is already written per release, for the words people use, and reviewed. docs/concepts/ is for maintainers: it describes code, which would mislead an agent talking to a person.
  • No tools of its own: the agent shouldn't have to choose a tool; one search over every level tells it where each answer came from. The lead can't open files, so tools are needed anyway; workers get the same ones.
  • Search is Grep, run by ripgrep, the program Claude Code's Grep runs: patterns cover a word's variants, which word matching misses, and the answer comes in the same turn. Handing the question to a worker would cost a container and a second model run for the same search.
  • No preloaded glossary: the description's "names a place… you don't recognise" is what fixes "MySpace". The tests (board 7) measure it; if it misses, the glossary goes into the instructions (about 1,500 tokens, cached).
