A site's page

office-server, opened from the Fleet tab.

What this is

  • One page, one site, on one machine. A site and its machine are separate things with their own names, though every machine carries one site. The lede says which machine the site is on. When a machine connects, the site's name starts as the machine's; after that they are stored apart, and a site that moves keeps its name (§6, §13). (2026-10-16: superseded by ADR-0120 — a site is always named after its machine, and a move or a restore renames it after the new one.)
  • Two groups of cards. The site — what HQ uses, and what moves with it: its Execution Site (whether it takes part in HQ, runs against capacity), its version and any fix waiting with the maintenance window named (§11), its capacity (Edit opens page 4), and its backups, which show the backup location and cannot change it (page 9): office-server has none set, so the card gives the command to run on that machine. Then The machine, in its own tinted panel under its name — what stays with the hardware: its system, its health (disk, memory, processors; these figures never reach HQ, §2, §10), the protections (a fact, §8), and the host service, which lists earlier machines once the site has moved.
  • HQ's site is one page with three groups — The HQ (what people use: its address and health, its version, the organisation's connection to Agenthix Cloud, backups), The site (the default site, where HQ's own agents work) and The machine, once. HQ never runs without its default site, and they upgrade, back up and move together.
  • Actions under the title, with one primary (Upgrade…; Back up now on HQ's site): Upgrade…, Resize… and Move site… (to a new machine), each its own action whose dialog asks Now, or schedule for later? (the Scheduled screen lists what is scheduled), logs, disconnect (page 7). HQ's site adds Back up now, Move HQ… and Open HQ ↗. Only changes from the closed set appear (§6). It opens from a site's card on the Fleet screen (page 2).

hq-box — HQ's site

HQ's site has its own page, with The HQ, The site and The machine: see HQ's site. The Fleet's hero card opens it.

Add a site

Adding a site needs both sides: a fleet admin here, a machine admin on the machine that will run it (§6, diagram 7). Each machine carries one site, which takes the machine's name to begin with.

What this is

  1. The fleet admin chooses Add a site and gets a one-time code, with the command to hand over.
  2. The machine admin runs agenthix console connect <hq address> <code> on the new machine. It prints the machine's fingerprint and waits.
  3. The Fleet Console shows the machine's name and fingerprint; the fleet admin compares and confirms. Both sides then pin each other's identity.
  4. The host service starts the machine's site, and the Fleet Console registers the site's credential with hq. The site takes part at once: no organisation admin approves it. Cloud adds its sites the same way.

Two choices. Add a site first asks what is being added: a new site, or Restore from a backup — a site whose machine was lost, brought back on a new machine from its backup (in the backup location, or an export file) and its key. Connecting the machine works the same way either way. If the machine that holds hq and the Fleet Console is lost, none of this is available — the Fleet Console was on it, unless it runs on another machine (it does not move when hq moves). Run agenthix restore --from <location or file> on a new machine instead: it brings back hq, its default site and the Fleet Console.

After any restore, hq and the site reconcile and hq says plainly what was lost.

Editing capacity; protections as a fact

From the Capacity card on a site's page.

What this is

  • Capacity is the site's, and it opens from the Capacity card on the site's page: memory, processors and processes for each agent run, and how many run at once, on the machine under it. HQ and project policy may only narrow them (§8).
  • Protections belong to the machine, not to capacity. They are a fact, not a setting (§8): agents can't reach this machine, its other containers or the cloud metadata address. No control, no switch, no “allow a port”, in the Fleet Console or on the command line. Only capacity is editable, and its page says protections are not set there.
  • When the rules do not hold, the Protections card in the machine panel says so in a sentence with the next step, and that no new agent starts until they hold.

Disconnecting a machine

From either side: Disconnect here, or agenthix console disconnect on the machine, which works at once even when the Fleet Console cannot be reached (§6).

What this is

  • Disconnecting ends management only. The machine's site (or hq) keeps running and keeps taking part in hq. Removing a site is done on its machine; hq has no control over sites.
  • The dialog names what stays: the site, its nightly backups on the machine, its backup location, and scheduled changes that stay with the machine.
  • hq's own site, hq-box, offers no Disconnect: the Fleet Console runs on it.
  • Either way the card stays in the fleet, saying who disconnected it and when, until someone removes it from the list.

Moving a site

A site moves to a new machine — new hardware, a bigger server — with Move site… on its page. Spec §13 (A site moves), §14.

What this is

  • Nothing connects to a site, so no address changes: the site keeps its name, credential and workspaces; it dials hq from the new machine as it did from the old. (2026-10-16: superseded by ADR-0120 — a site is always named after its machine, and a move or a restore renames it after the new one.)
  • The new machine connects with a one-time code from the dialog and waits to receive the site — it starts none of its own, so one site per machine holds.
  • The site is read-only from the final backup to the switch, with notice; its runs pause and resume. Removing the old copy is the last step, not an erase, and the old machine leaves the fleet.
  • hq's site has no Move site…; it moves with Move hq…. A Cloud site has none either. On the machine: agenthix site schedule move --at <time> prints the same code.

Today

No way to do it: a site on a new machine is a new site, and its workspaces stay behind.
