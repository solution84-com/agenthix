Where work runs — the list

One read-only page for an organisation admin: each site, how it is doing in a sentence, its runs against its capacity, what each run gets, and where it runs. Nothing on it can be changed.

What this is

Organisation › Settings › Where work runs. Spec §10 (decision 4): hq has no control over a site, so this page shows and never acts. Organisation admins look after the business's people and projects; fleet admins look after the machines. If a site goes down, the organisation admin sees it and why here, and speaks to the fleet admins, who have already been told. A site takes its machine's name, and a machine has at most one site (hq-box is hq and its built-in site).

Today

Organisation › Infrastructure › Execution Sites: approve, deny, stop, remove and a capacity editor, with disk, Docker and version figures. All of it leaves hq: sites are added and run in the Fleet Console, and a machine's condition is a cause in words.

After

  • A sentence per site: Available, Busy (every run place taken, runs waiting) or Unavailable since 09:14: its machine isn't answering. Your fleet admins have been told. The cause is in words; the machine's figures never appear.
  • Runs against capacity and how many wait, the limits each run gets (memory, processors), Self-hosted or Cloud, and a scheduled change when one is set.
  • No buttons: no add, approve, limit, stop or remove. A footer line points to the Fleet Console. Cloud's sites sit first, as in the fleet.

The built-in site, when it is not connected

hq's own site says why it is not connected in its status sentence, naming the actual cause instead of one guess. No controls.

What this is

The built-in site's page assumed one cause, though pairing can also be refused for a short secret or an address the site cannot reach. The host service on hq's machine passes the site's refusal to hq over its control socket, and the default site reaches hq over a private Docker network, not localhost. This is the same Where work runs page; only the sentence differs. Fleet admins have been told, and fix it in the Fleet Console or on hq's machine.

After — three causes, each named

Scheduled changes, as members see them

How someone whose work is affected hears of an upgrade, resize, restore or move scheduled on the machine their project runs on — from the moment it is scheduled until their runs carry on.

What this is

Spec §14: a scheduled change is set in the Fleet Console (its own dialog: Upgrade…, Resize…, Restore…, Move hq…), with the CLI (agenthix schedule), or by Cloud, and held by the machine's host service; hq hears of it through its control socket or from the site. From scheduling, hq shows a notice to the members whose work is affected; a few minutes before, no new runs start on what is affected and running agents finish their current step and pause; after, paused runs resume; if it fails, the host service rolls back and hq says so. A change or cancellation sends an updated notice.

Today

No screen: nothing is scheduled, so nobody is told and runs fail when a site goes away.

After — the notice from scheduling

  • On each affected project, until it is over or dismissed. For a scheduled change on a site, the members of that site's projects see it; for one on hq's own machine, everyone in hq does (drawn below). Organisation admins see it on Where work runs, never who scheduled it.
  • It names the site (not the machine), the time, how long, what will happen to runs, and that nothing is asked of them.

After hq moves, and uploads on a bare network address

Two things hq says about how it is reached: which sites followed it to a new address, and why uploaded files are downloads only when hq has no domain.

What this is

Moves (spec §13): an hq without a domain tells each connected site, and each machine's host service, its new address before it stops; they check the new hq with a challenge and answer on their own credential. The Fleet Console does not move with hq: it stays on the machine it runs on and dials hq's new address like every site. hq is read-only from the moment the move's backup starts, with notice. A site that was offline keeps trying the old address until agenthix site hq-address <address> is run on its machine; a machine that was offline needs agenthix console hq-address <address>. Changing hq's address on the same machine is a move too. hq — restored at the new address — knows every site and which have not connected since.

Uploaded files (spec §16): served from an origin of their own; on a bare network address there is no subdomain, so hq serves uploads only as downloads, and its settings page says so.

Today

No screen for either: moving hq is done by hand.

After — Where work runs after a move

  • A box on Where work runs until every site has followed: how many followed, which has not, that fleet admins have been told, and who acts. It carries no buttons.
  • The site that has not followed reads Unavailable with the reason in its row. Host services follow the same way; a machine that was offline is named in the box.

The fleet admin role, as hq shows it

Fleet admin is a role on an hq account. hq shows who holds it and never lets an organisation admin change it.

What this is

The Fleet Console has no accounts of its own: a fleet admin signs in with their hq login, and the role lives on that account (spec §7). The first account made at install holds both the organisation admin and the fleet admin roles. After that the role is given only by a fleet admin, in the Fleet Console's Fleet admins tab, or by a machine admin of hq's machine with agenthix hq fleet-admin <user>. An organisation admin cannot give it, so hq shows it as a read-only role with the words "Given in the Fleet Console". Every grant and removal is announced to all fleet admins and organisation admins.
