Design pass · 7 · The workspace view · settled 5 Nov 2026

Settled design

Overview: what changes

future state

The workspace view stays a full-screen place to review and merge code work. What changes: it opens on something useful, its conversations can always be found again, a branch that has fallen behind or clashes has a button that fixes it, narrower windows keep their lists, and a person who cannot open it is told why.

How it fits area 2. The view keeps its own full-screen frame (‹ back to the project, no left rail), because reviewing a diff needs the width. Its right side becomes the same chat panel and bar as everywhere else, untouched by browsing. Any conversation can ask an agent to change the workspace. One way to talk, everywhere.

The five critical problems, and the answer to each

  1. A person without access waits on endless Loading → a page inside HQ that says why, who to ask, and links back (Can't open a workspace).
  2. A started conversation disappears after a reload → the view has no conversations of its own; the chat is the app's panel, kept through reloads, and a branch links to the conversation it came from (The conversation in the view).
  3. A merge clash is a dead end → the top-right button becomes Bring up to date, then Updating…; no extra notes (Behind main and clashes).
  4. Smaller windows hide every list behind unlabelled icons → the left panel stays open with labelled tabs; the chat goes over the page instead (Laptop and tablet).
  5. Turning Git on is permanent, but the dialog doesn't make that clear → a deliberate step that says it up front, and a note afterwards saying what changed. Git stays opt-in (Turning Git on).
Not changing what the product does. Every item above uses what already exists: bringing a branch up to date is the agent's existing job, now started from a button; the conversation list reads conversations that are already stored. Git on by default would be a change of behaviour; it stays your call, and the default here keeps it opt-in.

What changes

  1. The branch is in the breadcrumb: Website relaunch / website-code ▾ / ⑂ login-page ▾ (🔒 main). The picker box in the left panel goes.
  2. Its details are hidden in its menu. Each branch is one row: who, how many changes, and "behind main" only when it is. The bottom status line and the repeated counts go.
  3. One next-step button, top right, beside About: Merge into main… on a branch; nothing on main.
  4. It opens on something. On a branch: the first changed file, with its changes. On main or without Git: the README, otherwise the first file. Never "Choose a file…" alone.
  5. The left panel is one file tree: the files as they are on the branch in view, with the branch's changes marked (M, A, D) and Only changed to narrow it. Opening a file shows the whole file with its changes in place. See Files and changes, one view.
  6. Versions are the last part of the breadcrumb on main (see Files and changes, one view).
  7. The chat is the app's chat panel, untouched by browsing; any conversation can ask an agent to change this workspace (see The conversation in the view).
  8. Deploy… moves into About.

What changes

  1. One view for files and changes. The tree is always the workspace's files as they are on the branch in view; the branch's changes are marked in it.

Why: a list of changes and a list of files showed the same files twice. Marking the changes in the tree gives one place to look, and seeing a change inside the whole file shows what it does.

The conversation in the view

future state

The right side is the app's chat panel, nothing more. A person talks to any of their agents, in any conversation, and asks one of them to make a change here. The workspace view does not own conversations and does not tie the chat to what is being browsed.

Where a branch comes from

When an agent's work changes a workspace that has Git, the work gets a branch of its own, wherever it was asked for: in a project conversation, in Your space, or by a task. The branch remembers where it came from, as a link, so a person can always get back to the reason for a change. Nothing else depends on it.

Each branch has one chat of its own: 💬 in the breadcrumb

On a branch, the breadcrumb ends with 💬 Chat, as main ends with its version. It opens the branch's own chat in the panel: the conversation the branch came from (or, for a task's branch, the task's conversation). There is only ever one per branch. Nothing opens it but that click.

Each branch in the menu says where it came from (💬 a conversation, or a task). It is the same chat 💬 opens.

What changes

  1. No conversation belongs to the view. The panel is the app's, unchanged by browsing; "main has no conversation of its own" and the workspace-only ＋ go.
  2. A change is asked for in any conversation with an agent of the project (or of Your space for a personal workspace).
  3. Each branch has one chat of its own, opened from 💬 Chat at the end of the breadcrumb; main ends with its version instead.

Getting back to a conversation

future state

Today a conversation started in the view vanishes after a reload. With the app's panel there is nothing to vanish: the conversation is the panel's, kept as the person left it, in the view and out of it.

  1. The panel keeps its conversation through a reload, entering and leaving the view, as everywhere in the app.
  2. Every conversation is in Conversations on the bar, newest first, as settled in area 2. No workspace group, nothing special.
  3. From a branch, its origin is one click: the branch ▾ menu's "from 💬 Launch checklist" (see The conversation in the view).
Why: the critical problem was a conversation owned by the view and lost with it. Not giving the view conversations of its own removes the problem rather than patching it.

What changes

  1. No notes, no extra lines. Behind, clashing or updating is said by the one button and a ◌ on the branch; the detail is on hover, in the branch menu and in the conversation.

Why: today a clash is a dead end with only a promise. The agent already brings branches up to date; one button starts it, and the button itself shows it working.

Smaller fixes and words

future state

Defects, fixed without a decision

  1. A person without access sees "Loading…" with no end (now Can't open a workspace).
  2. The branch picker's second line is cut off exactly where the "behind" count sits: the picker wraps instead.
  3. "Download" is disabled on every file with no reason: it works for a file; when it can't (too large, a folder), it says why.
  4. On a phone the open file's name is cut to "A.." and Download runs off the line; code runs off the right edge (now wrapped).
  5. The phone view has no workspace switcher and no About (now in ⋮).
  6. A task's message box placeholder is cut off: shortened to "Message about this task…".
  7. "case-study-drafts's files": possessives after a name ending in s read "case-study-drafts' files", or the sentence avoids one.

Words

  1. Git words explained where they appear: ahead, behind, protected and the M / A / ✕ marks each carry a short hover explanation (and a legend under Changes on a phone).
  2. One word for a saved point: version. "Commit" is not shown on screen; main's versions list them.
  3. "Repository" means only the copy on GitHub; Git on the site is "Git" ("Keep versions with Git").
  4. A button never shares its name with the dialog it opens: "Merge into main…" opens a dialog whose button says "Merge login-page into main".
  5. Workspace rows say they open a full-screen view (an ↗ mark and "Opens the workspace view").
